### Ground truth found in code (2026-09-25)

**"trans removeCustomerFromClinic" is not one function.** In `LIS-transformer` (v1, NestJS) there are
**two** call sites into core's gRPC `RemoveCustomerFromClinic`:
1. `src/utility/utility.service.ts:3241` — `deleteCustomerProfile()`, reached from
   `src/utility/utility.controller.ts:535` `@Delete('/removeCustomerFromClinic')`
   (guards `CustomJwtAuthGuard` + `PermissionGuard`, `@RequirePermission({...INVITE_USER_MGMT_WRITE,
   clinicParam:'clinic_id'})` — VP-17647). This is the real "admin removes a member" path.
2. `src/setting/setting.practiceInfo.service.ts:9913` — `removeInvitation()`, only when
   `invite_status === 'Account Pending'`. A pending-invite account is unlikely to hold a LIVE
   integration, but it is the same removal semantics, so a shared helper should cover it.
`LIS-transformer-v2` does **not** call it (only `practice-audit-log.service.ts` / `rbac-audit-log.service.ts`
reference the event name string `removeCustomerfromClinic` — note the lowercase 'f', kept verbatim
to match the writer).

**trans has ZERO existing calls to lis-backend-emr-v2.** grep over `LIS-transformer/src` for
emr-v2 / EMR_V2 / lis-emr: no hits; no EMR entries in `.env.example`. VP-18404 introduces the FIRST
trans -> emr-v2 dependency, which means a new base-URL env var in the trans ConfigMaps for staging
and prod, plus an auth decision (see below). trans already uses `HttpService` widely
(`trans.service.ts`, `dashboard.service.ts`, `valogin.service.ts`, …) so the transport itself is routine.

**Auth is the real open question.** emr-v2 has exactly two auth primitives:
`src/modules/auth/guards/jwt-auth.guard.ts` (`JwtAuthGuard`) and `@Public()`. There is **no**
service-to-service API-key / internal-token guard anywhere in `src/modules/auth`. The integration
controller is `@UseGuards(JwtAuthGuard)` + `@SkipDataAccessCheck()` (VP-16980: any authenticated
user may reach it; the customer/clinic data-access check is skipped for this controller only).
`deleteCustomerProfile` already receives the caller's bearer token
(`utility.controller.ts`: `headers['authorization'].split(' ')[1]`), so JWT pass-through is available
without inventing a new mechanism — and it makes `last_modified_by` the real human who did the
removal, which is what PH-917 wants preserved in history.

**What core does on its side** (`LIS-backend-v2-coreSamples/service/customer_service.go:1532`
`RemoveCustomerFromClinic`) — useful because it defines what "the removal succeeded" means:
- emits audit log `removeCustomerfromClinic` (async goroutine, `common.RecordAuditLog`)
- **only if the customer is actually in the clinic**: removes the clinic edge, drops 3 Redis keys,
  inserts a `CustomerClinicRemovalRecord` history row (best-effort)
- always: strips RBAC roles, deletes `customerRoleOnClinics`, reassigns patients to a clinic admin
- **returns `success`/200 even when the customer was never a member of that clinic** (deliberate,
  to mirror v1). So trans CANNOT use "core returned 200" as proof that a relationship was actually
  removed — if the deactivate call is gated on the core result, it will also fire for no-op removals.
  Harmless (AC 3 says no-op when there is no integration) but worth stating.

### Lesson injection (WORK-LOOP Step 1.4)
From `framework/ENGINEERING-LESSONS.md`:
- **"`void somePromise()` 丟棄的是回傳值，不是 rejection"** — AC 2 asks for exactly a best-effort
  side call. Any promise we do not await needs an explicit `.catch()`, plus a try/catch if the callee
  can throw synchronously; and the test that proves "this side branch failing does not break the
  removal" must use a real `mockRejectedValue`, not a synchronous throw.
- **"會 fail-open 的 gate 要計數"** — "failure is visible rather than silent" must mean a distinct
  logged/Sentry outcome, not a WARN line that looks the same as success.

## Approaches Considered

**Where to put the call.** Core calling emr-v2 directly was rejected upstream (Fan Zhou, recorded in
the ticket) so core keeps no knowledge of EMR. Within trans: a single shared service injected into
both call sites, vs duplicating an axios call at each. Chose the shared service —
`src/trans/emr-integration-deactivate.service.ts`, mirroring the existing
`charge-balance.service.ts` shape (axios, `*_BASE_URL` env, bearer re-attachment, timeout, fail-soft).

**Awaited vs fire-and-forget.** Fire-and-forget was rejected: the injected ENGINEERING-LESSONS rule
is that a floating promise's rejection becomes an unhandled rejection, which modern Node turns into
a dead process — a best-effort side branch killing the service it hangs off. Awaited inside its own
try/catch instead.

**Return shape.** A boolean was rejected for AC 2: four distinct outcomes
(`deactivated` / `noop` / `not_configured` / `failed`) so a silent fail-open cannot read like a clean
success in the logs.

## Decisions Made

- Both call sites wired, not just `deleteCustomerProfile`. `removeInvitation` ('Account Pending')
  calls the same core RPC, so it carries the same consequence; an invitee rarely holds a LIVE
  integration, in which case emr-v2 answers noop, and covering it costs one call.
- Gated on core returning 200. On a core failure the relationship still stands, and deactivating
  then would disconnect a provider who was never removed.
- Accepted that core answers 200 even for a non-member (deliberate v1 parity, see Ticket Analysis),
  so a no-op removal also fires the call. Harmless — emr-v2 answers noop.

## Failures

**The first version broke AC 2, and a test caught it.** The call was awaited inside the method's
existing try, so a rejection from the deactivate service landed in the outer catch and
`deleteCustomerProfile` answered 500 — for a removal core had ALREADY applied. The admin would then
retry a removal that already happened. Caught by the `mockRejectedValue` test written before the
assertion was made to pass; fixed by giving the call its own try/catch inside the outer one.

The general shape, worth keeping: **a service that contracts never to throw does not excuse the
caller from handling a throw.** The contract is a property of today's implementation; the caller's
correctness should not depend on it holding. The ENGINEERING-LESSONS rule about `void promise` says
to use a real rejected promise in the test rather than a synchronous throw — that is precisely what
made this visible.
