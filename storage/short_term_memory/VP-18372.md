### [2026-09-24] The actual code gap found instead: the HL7 never says "corrected"
`src/modules/grpc/services/sample-test-result.service.ts:429` — `status: 'F', // Final status`,
hardcoded for every test, every push.
`src/modules/hl7/services/hl7-encoder.service.ts`:
- `:372` OBR-25 Result Status — hardcoded `'F'`
- `:666` PDF OBR OBR-25 — hardcoded `'F'`
- `:599` / `:442` OBX-11 — `test.status`, which is the hardcoded `'F'` above
- `:295` ORC-5 — `isFirstPanel ? 'F' : 'C'`; the `'C'` is a per-panel sequencing artifact, NOT
  amendment awareness
- `:233` MSH-10 — a fresh timestamp per push, so the re-push is NOT a control-ID duplicate
- `:223` MSH-9 — always `ORU^R01`

=> A re-pushed amended result is byte-wise indistinguishable to the receiving EMR from a brand-new
final result: same filler order number (OBR-3 = accession), OBR-25 = F, OBX-11 = F. HL7 v2's
convention for an amendment is OBR-25 / OBX-11 = `C` (corrected). A receiver that dedups on
(filler order, result status) or that refuses to overwrite an existing Final will silently keep the
old values — which matches JAG's complaint far better than "we never re-sent it".

### [2026-09-24] Event-shape facts for scope item 1 (if it is still wanted)
- `amended_sample_finished` (lis-result): EXISTS. Carries `sample_id`, `accession_id`;
  `customer_id` null, `clinic_id` 0, `addon_column` `{}`. Fires ~5 min BEFORE `report_finished`.
  For the result-re-approval class it is **redundant** — `report_finished` already re-fires and is
  the only one of the two that carries customer/clinic. Subscribing to it would only add a second,
  earlier, duplicate push per amendment.
- `personalized_report_cache_cleared` (lis-report): `sample_id` 0, `customer_id` null,
  `clinic_id` 0, `products` = report LONG name, `accession_id` populated. This is the ONLY signal
  for the report-content-only amendment class (VP-18194 measured that class emits no
  `report_finished` / `personalized_report_ready` at all). Resolution seam already exists:
  `getSampleIdByBarcode` + `resolveSampleClient`, used today by `handleNewReportStatusUpdatedEvent`.
  Volume NOT yet measured (the ClickHouse MCP tool needs a key, so no aggregate) — VP-18194 called
  it high-volume; on 2607136208 it appeared once in 51 events.
- BullMQ `add()` supports `delay`, so the requested 3-5 s wait is a one-option change in
  `ResultQueueService.addResultGenerationJob`.
- Whole-order path has NO dedup shield: `handleMessage` enqueues a job on every accepted event
  regardless of `ensureTransmissionRecord` reuse. Only the VP-17344 partial paths shield
  (`enqueuePartialPush`, `repushAfterMs`).

拆出來的規則：
1. **短到不能再短。** 一個訊息一個重點，Slack 分行發，不用段落、不用小標、不用 bullet。
2. **只發查到的事實 + 時間。** 「17:35 重發 report_finished、17:35:46 push 的」— 有時間戳、可驗證。
   推論一律不發。我草稿裡的 OBR-25/OBX-11 假說、`amended_sample_finished` 要不要訂的取捨，
   全部被拿掉 —— 那些是內部討論，不是對 PM 的第一則回覆。
3. **不 assume。** 不替對方的系統決定發生了什麼。先問一個具體、可回答的問題
   （「有沒有收到這一份？」），讓事實決定方向。
4. **把分岔講出來但不選邊**：「如果有但他們以為是重複的不理會，那改的方向會不一樣」——
   讓對方知道這個問題為什麼重要，但不先講第二條路要怎麼修。
5. 技術細節（vendor 名、筆數、TRANSMITTED 狀態、兩條 integration）**留著備用**，對方追問再給，
   第一則不塞。
