## Approaches Considered
1. **Route the manual push through BullMQ** (the infra the gRPC-timeout fallback already uses).
   Rejected: queue jobs carry `push_scope_key`, so for a PER_REPORT_GROUP integration this would
   change *what* gets pushed, not just when the caller is answered. Too big for a 504 fix.
2. **Raise the gateway timeout.** Outside this repo, and 80-90s responses are the wrong shape
   regardless. Mentioned to Leo as the infra-side alternative.
3. **Detach the existing run, answer 202** (first cut, then demoted). Generation path unchanged;
   only the response timing moves. Adds a status endpoint so the 202 is actionable.
4. **Raise the gateway timeout so the call finishes and returns 200** — **Leo's decision
   2026-09-17**: "以後都要等到結束回 200". Became the primary direction; option 3 demoted to an
   opt-in escape hatch for the pushes no budget can cover.

## Why it is slow (evidence, for the perf follow-ups)
- `sftp.service.ts:235` `uploadChain` — **every outbound HL7 upload in the service is serialized
  through one promise chain**, because `SftpConnectionService` is a single-client singleton
  (VP-17217 Phase 2b, added to fix a real socket race). A push therefore queues behind unrelated
  traffic to other vendors.
- Same payload, different vendor: sample 2616458, 6.22MB, same moment — vendor 9 post-generation
  15s, vendor 1 37s. Per-vendor 30d averages at ~5-6MB: vendor 3 = 1.0s, vendor 7 = 1.4s,
  vendor 1 = 20.9s (max 166), vendor 6 = 41.2s, vendor 8 = 47.1s. A ~40x spread at equal size.
- Each upload does a full connect → put → disconnect; an observed connect alone took 4571ms.
- Generation time is a smooth 2-68s tail **uncorrelated with file size** (24MB took 37s, 5MB took
  49s). I hypothesised this was the 10s-base exponential PDF-download retry backoff
  (`pdfDownloadBaseDelayMs = 10000`, 3 retries) but the histogram shows **no clustering at
  10/30/70s** — hypothesis not supported, do not repeat it without new evidence.

## Side-findings (flagged, not fixed)
1. **Oversized file sent past the vendor limit.** `FileSizeValidationService` caps MDHQ/Cerbo at
   15MB; `result-generation.service.ts` step 5 logs the violation and sends anyway by design.
   `2608186766.hl7` went out at 24.2MB. Only 2 of 5,631 MDHQ transmissions in 90 days exceed 15MB,
   both for customer 4953. Cerbo-side acceptance is not observable from our side.
2. **Manual push ignores `result_push_level`.** Manual/API records have `push_scope_key = NULL`
   (one combined file); the automatic pipeline writes per-scope files (`SAMPLE_TYPE:…`, `GROUP:MAIN`)
   at ~5MB each for this customer. Plausibly why the manual file is 24MB.
3. Sample 2618571 has **no transmission record before today** — the automatic pipeline never pushed
   it at all (report finished 08-22). Not investigated; possibly the known silent-drop class. Worth
   asking whether other customer-4953 reports were never pushed either.
4. `total_processing_time_ms` only counts generation, not transmission — the column understates
   end-to-end cost, which is why the 504 was not obvious from the data.

## Retrospective

## Lessons Learned
- A 504 on this endpoint is a **reporting** failure, not a push failure. Before repushing anything
  on a "timed out" complaint, check `result_transmission_records` and the vendor SFTP — the work has
  very likely already landed, and a blind repush duplicates it.
- Synchronous HTTP over a pipeline whose runtime is set by payload size (PDF embed + SFTP upload)
  will cross any fixed gateway budget eventually. The durable record, not the response, is the
  source of truth.
- **Read the actual error body before theorising about which hop timed out.** A Cloudflare-branded
  504 means the ORIGIN reported a gateway timeout; Cloudflare's own is a 524. I built a whole
  recommendation on "Cloudflare's 100s ceiling is the constraint" before Leo pasted the page, and
  it was wrong. One artifact beat three tool-assisted inferences.
- The reported symptom timing ("約 1 分鐘") was off by 50% — the page timestamp put the cut at
  ~90s. Take user-reported durations as approximate until an artifact pins them.
