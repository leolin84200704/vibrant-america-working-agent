## Approaches Considered

### [2026-09-22] Options + PRO/CON debate synthesis

**Options considered**
- **A**: per-report PDFs as LOOSE FILES next to `{accession}.hl7`, driven by a NEW eligibility path on
  `new_report_status_updated` that is independent of `result_push_level`. (first draft)
- **B**: same PDFs, but delivered from the EXISTING VP-18138 attachment hook
  (`result-generation.service.ts:349-357`, after the record is TRANSMITTED), i.e. riding whatever push
  the integration is already configured for. (CON side's counter-proposal)
- **C**: embed N PDFs in the HL7, one ED OBX under each panel OBR. Needs `pdfReport` -> array,
  OBR/OBX loop, and a report-short-name -> panel-OBR mapping that does not exist. Touches the encoder
  path shared by EVERY vendor. Deferred: only Cerbo can say whether their parser accepts it.
- **D**: build the SPA URL ourselves and call `report-pdf-engine` directly. Rejected: emr-v2 would have
  to carry a copy of the `sections` flag grammar (which lives in the portal) and obtain
  `PDF_REPORT_UNIVERSAL_TOKEN_PROD`; the known failure mode of a wrong flag string is a SILENT 4 KB
  PDF. `getSelectedReportsZip` keeps that grammar on the LIS-Report side and works with the token
  emr-v2 already has (live-proven).
- **E**: express it as `result_push_level=PER_REPORT` + attach PDF. Rejected as the ONLY mechanism:
  push level is the HL7 splitting granularity, and Maristany is WHOLE_ORDER — the combination
  "one HL7 + split PDFs" would be unrepresentable. Kept as the TIMING mechanism (see synthesis).

**Accepted from CON (verified, not just argued)**
1. `result_attachment_records.result_transmission_record_id` is **NOT NULL** (prod information_schema)
   => option A has no record to hang an audit row on. This alone pushes the design to B.
2. **62 of 202 MDHQ clinics (31%) have more than one LIVE result_enabled integration row**
   (FOLLOWTHATPATIENT 8 of 20). LIS-7716's "arbitrary LIVE row wins `findFirst`" therefore is the
   COMMON case, not an edge case => a practice-level flag read off one arbitrary integration row is a
   coin flip. Fix adopted: **resolve the effective setting over the DESTINATION, not the row** —
   OR across all LIVE result_enabled rows sharing `(legacy_emr_service, sftp_result_path)`, falling
   back to the vendor default when every row is NULL. Deterministic whichever row wins dedup.
   (Maristany itself has exactly 1 LIVE row, so the canary is unaffected either way.)
3. Cerbo **moves consumed files to `archive/`** => re-uploading the same filename after the partner has
   already fetched it is NOT an idempotent overwrite, it is a SECOND document in the chart. And a
   put landing while their poller reads the same name can be ingested truncated (0.5-1.5 MB files
   widen that window a lot vs today's small HL7). Adopted: publish atomically via `.part` + rename,
   and the amended re-delivery naming contract must be agreed with the partner before shipping.
4. Ordering hazard: a per-report PDF delivered on report-final can land DAYS before `{accession}.hl7`
   exists for a WHOLE_ORDER integration => an orphan document. Adopted: deliver from the push, not
   from a separate trigger.
5. SFTP cost: `uploadHL7File` is connect -> ensureDir -> put -> disconnect and every call is pod-wide
   serialized (`runSerialized`, VP-17217). 1 -> 1+N files per order multiplies the serialized round
   trips and queues OTHER integrations' HL7 behind our PDFs. Adopted: one session per pass that puts
   all N files.
6. Event storm: `new_report_status_updated` fires on ready AND viewed; a push-level-independent path
   would delete the `getActivePartialPushLevels()` fast-return for 202 Cerbo clinics. Moot under B.
7. split=0 AND combined=0 is reachable and silently removes every PDF. Adopted: reject/alert on that
   combination.
8. A size floor alone cannot separate a 4 KB stub from a legitimately short report. Adopted: the
   primary check is entry-count + entry-name match; size floor is only a backstop; failures alert.
9. `is_amended` absent (non-prod env gate) must be a THIRD state (unknown -> alert), never folded into
   `false`.

### [2026-09-22] MEASURED: what an amendment actually emits (general_sample_events, prod)
`amended_reports` is written in BATCHES tied to a LIS ticket, never one-off:
2026-05-19 MEG x102, 05-21 MEG x22, 06-22 NTG x183, 07-17 NTG x39, 07-29 GUT5 x1 + OAC x1,
07-30 OAC x14. Total 362 rows / 355 barcodes. Two DIFFERENT physical shapes:

- **Amendment that came with a RESULT RE-APPROVAL** (barcode 2604286803, OAC, 07-30 18:17-18:18Z):
  `products_finished` -> `sample_type_all_finish` x2 -> `results_all_finished` -> `sample_finished`
  -> `personalized_report_cache_cleared` x N -> **`personalized_report_ready`** ->
  **`report_finished` 18:18:14** -> more cache_cleared.
  => `report_finished` IS re-emitted, and emr-v2's existing whole-order push path already consumes it.
  If per-report PDF delivery hangs off the push, this class of amendment re-delivers with ZERO extra code.
- **Amendment that is a REPORT-CONTENT-ONLY correction** (barcode 2602026370, MEG, row added 05-19,
  cache cleared 05-26 21:38Z): the ONLY events are `personalized_report_cache_cleared`
  (one per report, products = LONG name, sample_id 0 / clinic_id 0 / customer_id null).
  **No `report_finished`, no `personalized_report_ready`, no `new_report_status_updated`.**
  => this class emits nothing emr-v2 consumes today; no configuration of the practice can make us
  notice it. This is the real content of the "amended -> resend all" AC.

Consequence for the design: the trigger question is NOT "which event do we subscribe to" but
"how do we notice the content-only class". Cheapest complete answer = a periodic sweep over orders
already delivered for split-enabled integrations, comparing each report's
`(is_amended, final_report_date)` from `getReportStatusListV2` against the last
`result_attachment_records` row, and re-delivering the whole set on any change. Volume is bounded by
how few integrations have split enabled (Maristany ~1-2 orders/week, FOLLOWTHATPATIENT ~7/day), so a
30-day window is a few hundred status calls per run. Subscribing to `personalized_report_cache_cleared`
was considered and rejected as the primary mechanism: it is the only signal common to BOTH classes but
it is high-volume, carries no sample/customer/clinic, and still needs the same is_amended comparison
to filter noise - i.e. it only moves latency, not correctness.

## Lessons Learned
- **同一份產物有兩條取得路徑時，決定性的差異在壞輸入的失敗形狀**（詳見 Retrospective / factory PR #87）。
- **範圍裁決要建立在量過的事實上**：把「amended 有兩種形態、其中一種不發事件」量出來之後，
  「只做未來」才是一個知情的決定。沒量之前我只能問一個 Leo 答不了的問題。
- **宣告不實作某條 AC 時，要說清楚它是「沒補既有的洞」還是「做壞了原本會動的東西」**。
  這次 case 2 的缺口今天就存在於合併 PDF，所以 Jira comment 明講了「this ticket does not change it
  in either direction」，否則 PM 會把既有行為誤讀成本次退步。
