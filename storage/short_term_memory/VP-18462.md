## [2026-09-29 22:20Z] Shadow found a real difference — and I had been looking in the wrong place
- The three post-18:17Z `/proxy/grpc/getKitStatus` calls (18:33Z, 20:28Z, 21:02Z; trans v1 attribution IPs 10.224.1.123/0.209/2.145) WERE the shadow-mode setting-consumer pods (RS 85c594f668). They looked like unknown IPs only because Ray's #183 deploy (21:34Z, image 03d7a3b) replaced those pods at 21:43Z before I compared — shadow keys survived (envFrom), verified in the new pod.
- The shadow events exist: `service:lis-setting-consumer @call_function:grpcShadow`. The winston logger writes the CALL NAME into the JSON `service` field and the JSON payload into `@info`, so `grpc_shadow` as free text / `@event:` finds nothing. Three events, all `agrees:false`, identical difference: `send_out[0].packages[0].kit_name: missing in grpc; send_out[0].packages[0].pickup_time: missing in grpc`.
- Cause: `LIS-setting-consumer/protos/shipping.proto` `Packages` stops at field 3; trans v1's declares `kit_name = 4`, `pickup_time = 5`. (LIS-Shipping's own repo copy `src/protos/core-protos/shipping.proto` ALSO lacks them — the server evidently serves a newer schema than its repo copy; trans v1's file is the working reference.) `tests.proto` identical → getPatientTestsResult unaffected.
- Fix: draft PR LIS-setting-consumer `bugfix/leo/VP-18462-proto-sync` → main (copy trans v1 proto verbatim). setting-consumer deploys prod + staging from main. stage_test protos == main protos, no twin opened.
- Lesson (do not repeat): the 09-23 staging A/B used the proxy for BOTH sides' shape (probe script) and never decoded through this repo's proto; a shadow on real traffic found in 3 samples what the probe could not. Consumer readback through the consumer's own decoder is the only valid equivalence test for gRPC swaps.
