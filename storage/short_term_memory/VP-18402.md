# VP-18402 - Work Loop Record

## Ticket Analysis

Jira state at 2026-09-25 (L4 verified via Atlassian MCP):
- VP-18402 Dev To Do, P2, assignee Leo, reporter Xiaoye Li, created 2026-09-25 13:36 PDT, **zero comments**.

Problem (PH-917 wording): a clinic has Client A and Client B, both integrated. Client B is removed
from the clinic. The clinic<->customer relationship is gone, but B's `ehr_integrations` row stays
LIVE, so B still shows as integrated and an order submitted through Cerbo under that integration is
still accepted. PH-917 frames it as a **permission boundary** problem, not data tidiness.

### Ground truth found in code (2026-09-25)

**Why the stale row still routes orders** — `resolveOrderingIntegration` (emr-v2) picks the order's
customer from `ehr_integrations` filtered on `status='LIVE' AND ordering_enabled=true`, sorted by
typeRank then `updated_at` DESC. It never consults the clinic<->customer relationship, so a removed
provider's LIVE row keeps winning. (Skill `emr-order-customer-resolution`.)

**Result push has the same filter** — `result-generation.service.ts` (7 sites), `sftp.service.ts:126`
and `result-attachment.service.ts:251` all filter `status:'LIVE'`. So deactivating also **stops result
delivery** for that provider's already-drawn, in-flight samples. PH-917's AC says "existing
historical orders and integration history are preserved" but does not say whether in-flight results
must still deliver. OPEN QUESTION for PM.

**An endpoint that is 90% of half 1 already exists** —
`PATCH /integration-management/auto-integrate/requests/:id/disconnect`
(`integration-request.controller.ts:1110`, service `integration-request.service.ts:1486`):
- guards: `LIVE` only, else 400
- writes `status = REJECTED` (comment: "Using REJECTED to represent disconnected"), `updated_at`,
  `last_modified_by`
- creates one `ehr_integration_notes` row with the reason
- returns `status: 'DISCONNECTED'` (a string that is NOT in the enum — enum is
  PENDING/APPROVED/LIVE/REJECTED)
- **does NOT write `ehr_integration_status_history`** — unlike the manual LIVE->REJECTED procedure
  used in LBS-1784 / LBS-1785, which always inserted a history row.
Gaps vs what VP-18402 needs: keyed by integration **id**, not by (customer_id, clinic_id); one row,
not N; auth is a portal-user JWT.

**A provider can have more than one LIVE row in the same clinic** — proven by LBS-1785 (two
byte-identical LIVE MDHQ rows 7s apart; `create()` has no (customer_id, clinic_id) uniqueness
guard — LIS-7716 open). So the new API must deactivate **all** matching LIVE rows and report the
count, not `findFirst`.

**Re-add does not silently restore** — `create()` (`integration-request.service.ts:118`) validates
vendor/application/SFTP template and always INSERTs a new row; a REJECTED row is inert to
`resolveOrderingIntegration`. So that AC is satisfied by construction, no extra work.

**Half 2 (order-path validation) is a much bigger change than half 1.** emr-v2 registers five v2
gRPC clients (`grpc.config.ts:298` — customer / patient / sample / sales / setting, all package
`coresamples_service`). `clinic.proto` is vendored and does carry
`ListClinicCustomersByClinicID` / `GetCustomerClinicNames`, but **no clinic client is wired up and
no emr-v2 code calls one today** (grep: zero hits). Half 2 = new gRPC client + new ConfigMap env
vars + a new upstream dependency on the order hot path.

**What actually happens to an order once the integration is deactivated** (this is the "Before
starting: confirm what Cerbo does" question, answered from our side):
- `resolveOrderingIntegration` finds no candidate -> `customer_not_found`
- `markCustomerNotFound` (`hl7-order.processor.ts:576`) treats it as **RETRYABLE** (VP-17120):
  `parse_finished` stays false, `retry_num` decrements, the 15-min rescan retries
- when `retry_num` hits 0 -> quarantine row (VP-16166) + the VP-17544 Slack "order not placed" alert
- Cerbo/the practice sees **nothing**: the failure is entirely on our side.
So today a removed provider's order does not get a clean rejection — it burns ~hours of retry budget
and then surfaces in daily hl7_fail triage looking **exactly like** a "provider needs an integration"
misconfiguration, i.e. it invites the wrong fix (add the integration back). That is the strongest
argument for half 2 producing its own TERMINAL failure class (e.g. `provider_not_in_clinic`) rather
than leaving it as `customer_not_found`.

### Lesson injection (WORK-LOOP Step 1.4)
From `framework/ENGINEERING-LESSONS.md`:
- **"會 fail-open 的 gate 要計數"** — `gate_passed` and `gate_unavailable` must be two distinct
  outcomes. Applies to half 2: if the clinic-membership gRPC check is unavailable we will
  default-allow the order, and that must be counted and distinguishable from "checked and allowed".
- **"`void somePromise()` 丟棄的是回傳值，不是 rejection"** — applies to VP-18404's best-effort call.

## Approaches Considered

**Half 1 — how to address the integration.** Reuse the existing `:id/disconnect` endpoint (the caller
would have to look the ids up first, and there may be several) vs a new endpoint keyed on
(customer_id, clinic_id). Chose the latter: the caller knows the pair it just removed, not the rows.

**Half 1 — auth.** JWT pass-through (trans forwards the removing admin's bearer token; emr-v2 reuses
the controller's existing `JwtAuthGuard` + `@SkipDataAccessCheck`) vs a new internal API-key guard.
Chose pass-through: no new secret across two ConfigMaps, and `last_modified_by` ends up being the
real human, which is what PH-917 wants preserved.

**Half 2 — which RPC.** `GetCustomerClinicNames` is the cheapest shape but returns clinic NAMES only
— matching a clinic by name is not an identity check, so it was rejected outright.
`ListClinicCustomersByClinicID` (thin, FullCustomer) vs `ListClinicCustomerDetailsByClinicID`
(VP-18216 thick variant, purpose-built for clinic-scoped reads, carries `customer_id`, `isActive`,
clinic-scoped roles). Chose the thick one. Rejected adding a local cache: core invalidates its own
clinic caches on removal (`InvalidateCustomerClinicNamesCache`, `KeyGetCustomerAllClinics`), and a
second cache in emr-v2 would have invalidation nobody controls.

**Half 2 — fail-open vs fail-closed.** Fail-closed would halt every inbound order in the lab on a
single gRPC deadline. Chose fail-open WITH a distinct third outcome
(`in_clinic` / `not_in_clinic` / `check_unavailable`) per the injected ENGINEERING-LESSONS rule, so
"checked and allowed" and "could not check" are never the same log line. An empty roster is
`check_unavailable`, not "everyone was removed" — otherwise one bad response shape rejects a whole
clinic's orders.

**Half 2 — failure class.** Reusing `customer_not_found` was rejected: it is retryable (VP-17120), so
the order would burn its retry budget and then land in daily hl7_fail triage looking exactly like a
missing-integration config gap, inviting the one fix that re-opens the hole PH-917 closes. New
terminal class `provider_not_in_clinic` instead.

**結果 vs 初始假設.** The technical analysis held up: findMany-not-findFirst (LBS-1785), the route

**失敗分析 — three self-inflicted failures, all the same shape:**

1. **Over-engineering for stylistic consistency.** Made the trans caller an `@Injectable` service to
   match a sibling file. That one choice generated 4 module registrations, a DI spec, an edit to an
   existing spec, and a push-gate failure. Root cause: I optimised for "looks like the neighbours"
   over "smallest thing that works". Preventable — the ticket said "call an API", and I never asked
   whether a provider was needed. Fix shipped: module-level function, 8 files/+105 -> 2 files/+21.
2. **`git add -A` swept generated files into a PR.** An `npm install` re-ran prisma's postinstall,
   regenerating the version-controlled `prisma2/generated/` tree. Root cause: staging blind after a
   command that writes files. No gate catches this (pre-push checks build and DI, not diff content).
   Preventable by reading `git status` in full before committing.
3. **PR base chosen without checking divergence.** main and stage_test are bidirectionally divergent
   (165/105), so a main-cut branch aimed at stage_test rendered 137 files/+18580/CONFLICTING.
   Preventable in one command.

Common thread: **I did not look at my own output before handing it over.** All three would have been
caught by re-reading the artifact (diff, status, PR page) rather than trusting my intent.

**模式識別.** Leo's two interventions ("有需要改這麼多嗎", "這是對的嗎") were both about the same
failure mode, one turn apart. That is a signal, not a coincidence.

**教訓 — 下推檢查 (can it become deterministic?):**
| lesson | mechanism possible? |
|---|---|
| Never `git add -A` in a repo with version-controlled generated artifacts | YES — a pre-commit hook that refuses staged paths matching known generated dirs. Cheap, deterministic. |
| Check `rev-list --count` both ways before opening a PR | YES — a wrapper/checklist at PR creation; or simply always cut the branch from the target. |
| A before/after regression comparison is void for suites that cannot RUN | PARTIAL — can assert "executed suite count is equal or higher", mechanisable in a script. |
| Make a contract structurally true rather than defending it at each call site | NO — judgement, belongs in prose. |
| Don't swallow stderr in diagnostics; brace `${var}` in zsh paths | PARTIAL — lint-able, low value. |

**Factory 蒸餾檢查.** Portable (company names removed, still true, would recur in any environment):
1. Generated artifacts under version control + `git add -A` = shipping binaries. Hook-able.
2. A PR between bidirectionally divergent branches does not show your change — check both directions,

3. A before/after test comparison proves nothing about suites that never executed; count executed

4. Prefer making a contract structurally true (whole body in one try/catch) over defending it at
   every call site.
