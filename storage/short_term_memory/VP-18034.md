### Spec (third-party-payment-flow.md v2, the acceptance reference)

- Part 2 — platform JWT: header `{alg: RS256, kid}`, claims `iss=sub=platformId`,
  `aud=https://api.vibrant-america.com/v1`, `exp` 60 s out, `jti` random. Server: resolve key by
  platformId → verify RS256 → check aud + exp (small skew) → reject reused jti (shared short-lived
  store across instances).
- Part 3 — POST /orders: `Authorization: Bearer <provider token>` + `X-Payment-Authorization:
  Bearer <platform JWT>` + body `chargeIndicator: "T"`, `platformId`. Server: verify provider
  token → resolve platform record (key + card) → verify platform JWT → charge card → place order.
  platformId is a lookup hint, NOT authorization. Stax charge must carry
  `meta.transaction_initiation_type = MIT` + `meta.transaction_schedule_type = unscheduled`.
  Charge failure or no card on file ⇒ no order (same as C). VP-18032 additionally suggests binding
  the assertion to the order it authorizes.

## Approaches Considered

### [2026-09-03 12:45] Proposed design (emr-v2, VP-18032 + VP-18034 together) + debate synthesis

Design as presented to Leo (Step 4):
1. Controller: add 'T'; when T require `platformId` (400 MISSING_PLATFORM_ID) and
   `X-Payment-Authorization` (401 MISSING_PAYMENT_AUTHORIZATION); verify BEFORE the intake row
   is written; failures 401 INVALID_PAYMENT_AUTHORIZATION + details.reason; unknown platform 400
   INVALID_PLATFORM_ID. `platformId` added to the PH-861 type-check loop.
2. New `PlatformAssertionService` (VP-18032): jsonwebtoken RS256 pinned (`algorithms:['RS256']`),
   key from injected `PlatformKeyDirectory` (impl = client to Rui's VP-18031 record, URL via env;
   key looked up by the CLAIM iss, then iss==sub==body.platformId enforced; kid must be one of
   that platform's registered keys), jti replay via injected `JtiStore` (Redis SET NX EX, TTL ≥
   exp + skew; in-memory impl for tests). Redis down ⇒ fail-closed for T.
3. Mapper: T → ChargeMethod.CUSTOMER_PAY + `OrderFrontend.thirdPartyPayer = { platformId }`.
4. Finalizer: payer set ⇒ candidates from new `getPlatformPaymentMethods(platformId)`
   (`account_type=platform&account_id=`, response key `account_payment_method`), transactionPay
   with account_type 'platform' / account_id platformId. Guard/replay/indeterminate-stop unchanged
   (PRO verified: only finalizer :90 and :113-114 know the payer).
5. Two PRs: PR-A VP-18032 (service + tests, no wiring), PR-B VP-18034 (wiring).

PRO (verified in code): replay branch :74-81, failOnCustomerPayFailure guard :192-206,
indeterminate stop :169-177, VP-17497 persistence intake.service :288-297 are all payer-agnostic;
fhir-access.guard.spec already signs real RS256 JWTs with generateKeyPairSync — same pattern for
the new spec. PlaceOrderChargeMethod has no third-party value so customerPay is the only legal
mapping today.

CON (verified in charging code, ranked):
- **Critical — batch path**: `IsBatchPayment` (transaction_service.go:276-297) = ≥4 successful
  record_ids on the SAME payment_token in the 12-h UTC window ⇒ batch. A platform card pays for
  many providers, so the 5th order of the half-day WILL hit it; that branch (payment.go:1041-1084)
  posts the accounting Payment with `AccountType:"customer"` + `AccountID = JWT customer_id`
  (the PROVIDER), creates a status=2 pending transaction and returns
  `payment_transaction_id = "charging_v2_pending_batch_…"`, which emr-v2 (finalizer :129) treats
  as a completed charge. Also `AdjustChargeAmount` (stax_service.go:786-811) shaves $0.01 per
  same-amount charge on the same token within 5 min ⇒ charged ≠ `total` sent to Place Order.
- **High — no authz in charging**: `pay()` and `getAllSharedPaymentMethods` never call VerifyID;
  emr-v2's assertion check is the ONLY thing preventing charging an arbitrary platform. So the
  assertion must be bound to the request (VP-18032 "consider binding" ⇒ required), not optional.
- **High — jti vs placerId**: jti consumed in controller before the dedup ⇒ a retry replaying the
  same assertion gets 401 not `duplicate`; must be documented (new assertion per attempt). dryrun
  consumes jti but never touches charging.
- **Medium — semantics**: charge_method customerPay ⇒ order-management thinks provider paid
  (refunds/receipts). `GetStaxKey(orderCustomerId)` picks sandbox vs prod by the PROVIDER's id.
- **Medium — schema**: no payer column ⇒ reconciliation parses request_json; recommend nullable
  `order_intake.payer_platform_id` (manual ALTER before deploy).
- MIT/unscheduled meta absent in charging (VP-18089 AC #2 unmet).

Synthesis adopted into the proposal: (a) bind assertion to request (claim `placer_id` + `amount`
or body hash — needs Chris/PM since partners must sign it); (b) emr-v2 T path treats a
`charging_v2_pending_batch_` id as "charge did not complete" (fail-closed) until charging skips
batching for platform; (c) add `payer_platform_id` column; (d) charging-side go-live
prerequisites list for Fangyuan (skip IsBatchPayment for platform, fix batch AccountType, add MIT
meta, decide GetStaxKey for platform, accept provider HS256 token with account_type=platform).
