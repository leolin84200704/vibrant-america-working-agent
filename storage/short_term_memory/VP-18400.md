# VP-18400 — Integration Management 500 for customer 20048 (MEDHERO)

## What the response itself proves

Screenshot headers: `Content-Length: 52`, `Etag: W/"34-rlKccw1E+/fV8niQk4oFitDfPro"`,
`Access-Control-Allow-Origin: https://intelligence.vibrant-wellness.com`,
`Access-Control-Allow-Credentials: true`, `Access-Control-Expose-Headers: Content-Disposition`,
`Vary: Origin`, `X-Powered-By: Express`.

1. Recomputing Express's weak ETag over candidate bodies: only
   `{"statusCode":500,"message":"Internal server error"}` (lowercase "server error") yields
   `W/"34-rlKccw1E+/fV8niQk4oFitDfPro"`. That string is Nest's `MESSAGES.UNKNOWN_EXCEPTION_MESSAGE`,
   emitted by `BaseExceptionFilter.handleUnknownError` — i.e. a **non-HttpException** escaped.
   `InternalServerErrorException` would have produced "Internal Server Error" (different ETag), and
   grep confirms emr-v2 throws no explicit 500 anywhere outside the partner-api filter.
2. The CORS triple (reflected origin + credentials + `Expose-Headers: Content-Disposition` + `Vary:
   Origin`) is emr-v2's own `app.enableCors()` fingerprint (main.ts), so the body came from emr-v2,
   not from Cloudflare or the lisapi edge.

## The observability hole (this is why the ticket cannot be closed on evidence)

- Datadog, `kube_namespace:emr-v2`, 18:25:00–18:28:00Z: **5 log lines, all Redis RDB notices at
  18:27:24**. Nothing at 18:26:29. Pod `lis-emr-v2-deployment-prod-64c7d7f768-b6l5v`, image tag
  6f32319 (= current origin/main), running since 2026-09-24T22:28:25Z — no restart, no deploy.
- `service:lis-emr-v2-deployment-prod status:error` over 7 days: 41 patterns, **not one
  `ExceptionsHandler` entry**. Nest normally logs `exception.message + stack` there.
- Sentry: `initSentry()` only calls `Sentry.init({dsn, environment})`. No `@sentry/nestjs`
  `SentryGlobalFilter` / no `captureException` in the HTTP path, so unhandled request exceptions are
  never reported. Sentry is initialised in prod (`Sentry initialised (environment=production)`,
  2026-09-24T22:28:21Z) but has zero emr-v2 events.
- emr-v2 has no request logging middleware and no request id, so there is no route/user/latency trace
  either. APM keeps only diversity-sampled spans (one OPTIONS 204 survived from 18:17).

Net: a 500 on this service currently leaves **no** stack, no user, no route, no request id anywhere.

## Approaches considered

- **A (recommended)** Ask the reporter for repro details AND ship observability in emr-v2
  (global `AllExceptionsFilter` that logs method+url+query+userId+requestId+stack and calls
  `Sentry.captureException`, plus an `x-request-id` echo). Makes the next occurrence diagnosable in
  one look; behaviour-testable (filter unit test + e2e on a throwing route).
- **B** Observability only, no question to the reporter — cheaper but risks closing a live P1 blind.
- **C** Close as not reproducible — rejected: the ETag proves a real unhandled exception fired.

## Lessons applied (ENGINEERING-LESSONS)

- *Preserve evidence before restart* — no restart was performed; the pod that served the 500 is still
  the running pod and was interrogated in place.
- *Verified means live, not mock* — every conclusion above comes from prod DB, prod Datadog and live
  HTTP calls against the production URL, not from unit tests.
