# VP-18288 - Work Loop Record

## Ticket Analysis
Zendesk 757398 (follow-up of 748029). Client Account Manager reports provider 4478 / practice 4676
(ChiRho Chiropractic, vendor POWER2PRACTICE) still receives the Classic Complete Report in P2P
instead of Personalized Report - All Markers. Example accession 2608106309 = sample 2613027,
transmitted Sep 3 2026 04:05:20 UTC. Prior AI triage (Hermes) stopped at "current settings are
PERSONALIZED but the effective style at send time is unverified".

## Ground truth collected (all read-only)
- `lis_emr.ehr_integrations` clinic_id 4676 has **two LIVE rows**, both FULL_INTEGRATION /
  POWER2PRACTICE / sftp_result_path `/public/`:
  - `cmjklx0us00a50xfew21h8625` customer_id 4477, report_option **CLASSIC**, msh06 4477
  - `cmjklx0xw00a70xfexs9l34ma` customer_id 4478, report_option **PERSONALIZED**, msh06 4478
  LIS-7716's "sibling LIVE row shadows the setting" failure mode does NOT apply here:
  `result_transmission_records` has **zero** rows for the CLASSIC row; every push for this practice
  (checked back to Aug 27) used the PERSONALIZED row, including the disputed one.
- `ehr_integration_notes` has no rows for either integration -> report_option was never changed via
  the LIS-7716 PATCH endpoint. `last_modified_by` on both rows is still the May 2026 VP-16617 audit
  cleanup, and `ehr_integrations.updated_at` does not auto-update, so config history is unavailable
  from the DB. The style had to be established from the transmitted artifacts instead.
- emr-v2 code path: `report_option PERSONALIZED -> add_report 2 -> downloadPdfFromApi(style=advanced)`;
  `CLASSIC -> 1 -> style=classic`. Both resolved in `result-generation.processor.ts#getReportOption`
  (exact row by integration_id) and `result-generation.service.ts#buildClientConfigurationFromIntegration`.
- Datadog holds no emr-v2 log lines for sample 2613027 at all (the service's own
  `[generateResultHl7] enter ... add_report=N` line exists for other samples in the same minute),
  and the pod's `/EMR_storage/HL7Result_prod` volume no longer holds the file. The stored
  `generated_hl7_content` has the PDF bytes replaced by `[PDF_CONTENT_REMOVED_FOR_DB_STORAGE]`.
  Direct proof of the Sep 3 bytes is therefore unrecoverable.

## Method that settled it — byte-size reconstruction
`file_size_bytes` on the transmission record is the whole HL7 file as uploaded. The stored HL7 is
the same text with the base64 PDF swapped for a 36-char placeholder. So:

    implied_pdf_bytes = (file_size_bytes - (CHAR_LENGTH(generated_hl7_content) - 36)) * 0.75

## Why the disputed accession's size matches neither style
POWER2PRACTICE is absent from `FileSizeValidationService.vendorCompressionThresholds`, so it falls
to `DEFAULT` = **10MB compression threshold** (vendor limit DEFAULT = 20MB). Any source PDF over
10MB goes through `AdobePdfCompressionService` before base64. Every P2P push whose source PDF
exceeds 10MB lands at ~18-22% of the original:

| accession | implied | classic now | advanced now | ratio vs classic / advanced |
|---|---|---|---|---|
| 2608076204 | 2,739,834 | 13,515,348 | 15,164,996 | 20.3% / 18.1% |
| 2608076205 | 2,671,401 | 13,374,085 | 15,038,351 | 20.0% / 17.8% |
| 2608176211 | 2,692,809 | 13,451,396 | 15,114,214 | 20.0% / 17.8% |
| 2608076210 | 3,032,841 | 13,532,722 | 15,215,762 | 22.4% / 19.9% |
| 2608106309 | 2,533,527 | 12,041,982 | 12,669,806 | 21.0% / 20.0% |

So 2,533,527 is exactly what compression of a ~12.7MB personalized PDF produces. The ratio is the
same for both styles, which is why this one accession cannot be discriminated by size alone -
only by its neighbours in the same batch.

## Verification that `style=advanced` is the report the customer asked for
`pdftotext` on the advanced artifact for 2608106309 shows repeated `Nutrient Zoomer - All Markers`
section headers alongside `Nutrient Zoomer - Summary` (81 pages, narrative layout). The classic
artifact is 121 pages of tabular `FINAL REPORT` with no such sections. So `advanced` IS
"Personalized Report - All Markers"; there is no third variant to consider.

## Decisions Made
- **No repush performed.** The skill's Class A repush is for a result that failed to arrive or
  arrived wrong. Here the outbound artifact for the cited accession was the correct style, so a
  repush would re-upload an identical (re-compressed) document into a patient chart - an
  irreversible outward action with no expected change in what the provider sees.
- **No config change.** Both LIVE rows are as intended; the CLASSIC sibling is unused by the push
  path and changing it fixes nothing. Deleting/merging it is a separate LIS-7716 hygiene item.
- Jira comment drafted only, not posted (house rule).

## Open question that only the receiving side can answer
What document name and upload date does P2P actually show for 2608106309? The Aug 27-28 uploads in
the same chart are genuinely Classic, so a provider scrolling the chart would see Classic documents
that predate the switch. `acknowledgment_status` is PENDING on every P2P record, so we have no
receipt confirming what P2P ingested.

## Lessons Learned
- **Transmitted-artifact reconstruction beats config archaeology.** `ehr_integrations` keeps no
  history (`updated_at` does not auto-update, notes only written by the LIS-7716 PATCH path), so
  "what was configured at send time" is unanswerable from the config tables. But
  `file_size_bytes - (CHAR_LENGTH(generated_hl7_content) - 36)` recovers the exact base64 payload
  length of every past push, and the pdf-cache endpoint still serves both styles on demand. That
  turns a "unverifiable historical state" question into an exact byte comparison.
- **Pick a neighbour when the subject is contaminated.** The cited accession was compressed and
  therefore mute. The sample pushed 47s later on the same integration was not, and answered the
  same question.
- **Compression silently erases the style signal at ~20%.** Any P2P/DEFAULT-vendor push whose source
  PDF exceeds 10MB cannot be style-identified from its transmitted size. Worth remembering before
  concluding anything from a single large record.
- LIS-7716's duplicate-LIVE-row hazard is real for this clinic (two LIVE rows, one CLASSIC) but was
  NOT the cause here - always check `result_transmission_records.integration_request_id` before
  blaming the sibling row.
