# VP-18589 - Work Loop Record

## Ticket Analysis

### [2026-09-30 15:30] Origin and four-part analysis
Source: integrator message forwarded by Chris Wu (kit tracking screens polling
`GET /orders?placerId=` every 5 min). Three asks: (1) kit/lab never populate in
sandbox, are they populated in prod; (2) list said kit_delivered while lookup said
placed + kit:null for three W2W- placerIds on 2026-09-25; (3) is there any status
for delivery failed / lost / return failed / sample rejected.

1. 目的 — lookup and list must agree on the kit tier of `status`; carrier delivery
   exceptions must not read as `placed`.
2. 改前 (origin/main 6c1cb59):
   - `order-status.derivation.ts` derives kit progress ONLY from the live shipping
     gRPC (`OUTBOUND_RANK` / `RETURN_RANK`). `kit === null` (shipping degraded) →
     no kit signal → `placed`. Core's `order_kit_status` rides along on the same
     ListSamples response (`SampleOrderSummary.order.orderKitStatus`) but is unused.
   - Rank tables know 6 raw values; shipping actually emits 8 — `DELIVERY_EXCEPTION`
     and `VOIDED_SHIPMENT` (LIS-transformer getPatient.service.ts handles both) are
     skipped as unknown → contribute nothing.
   - `order-list.derivation.ts` `KIT_STATUS_LADDER` has voided but not
     `kit_delivery_exception` → unrecognized → `placed`. Prod warn 2026-09-29
     `[ORDER_LIST_STATUS] unmapped core status values for sample 2598251: kit_delivery_exception`.
   - Staging: `grpc.config.ts` leaves shipping host EMPTY on staging by design (only
     shipping service serves prod data). 334 `[ORDER_STATUS_KIT] kit status
     unavailable ... neither cloud nor on-prem client is initialized` 09-24..09-30
     + 129 `[ORDER_STATUS_CORE] sample not found in core` (row-only degrade).
   - Verified from the staging pod (lis-emr-v2-deployment-staging, ns emr-v2):
     on-prem 192.168.60.6:31995 (base-report-server's "STAGING" shipping addr) and
     :31865 both ECONNREFUSED; cloud `lis-shipping-service-grpc.shipping.svc.cluster.local:63142`
     OPEN but serves PROD kits → cannot be used for sandbox. No staging shipping
     service exists; shipping team's to provide.
3. 改後為何有效 — when shipping is degraded, derive the kit tier from core
   `order_kit_status` via the same ladder list mode uses → both modes read the same
   record → agree. Adding DELIVERY_EXCEPTION / VOIDED_SHIPMENT to the rank tables
   makes an exception-state package count as "left the lab" (kit_shipped /
   sample_in_transit) instead of vanishing.
4. 改什麼 — see Code Changes.

Docs (mintlify apidemo.mintlify.app/api-reference/orders/status, fetched 09-30):
status enum = the 8 documented values (no delivery-exception value); kit =
status/carrier/trackingNumber/shippedAt/deliveredAt; exceptions type enum = the
same 5 we implement + raisedAt; report.status includes `cancelled`, `availableAt`.
The 5 timestamp/carrier fields were DROPPED from the contract 2026-08-13 (VP-17760
comments 183880/183942: no upstream has them) — mintlify never updated (api-product
owns it). So "make code match docs" is only possible for the status derivation;
the field gap is a docs fix, not a code fix.

Lesson injected (ENGINEERING-LESSONS): "Verified means live, not mock" — the
staging reachability and the Datadog counts above are the live evidence; unit
tests on the derivation are the behavior pins.

## Approaches Considered
- A (chosen): status fallback to core kit ladder when `kit === null`; `kit` block
  stays null (shipping detail truly unavailable; null = degraded semantics kept).
- B: synthesize `kit` block from core too ({status, trackingNumber:null}) —
  rejected: blurs the documented "null = upstream unavailable" meaning and
  invents a kit.status without tracking.
- C: point staging at the cloud shipping svc — rejected: prod data.

## Decisions Made
- Ticket VP-18589 filed as Task (own scope rule), assignee Leo, linked Relates
  VP-17760. Leo's instruction 2026-09-30: 「全部按照文檔先做完，然後給我回覆客戶的 comment」.
- DELIVERY_EXCEPTION mapping: outbound → kit_shipped (kit block `shipped`),
  return → sample_in_transit; core kit_delivery_exception → kit_shipped. The
  documented enum has no exception slot; surfacing it further = contract extension.

### [2026-09-30 15:35] Branch feature/leo/VP-18589 (worktree .worktrees/vp18589, off origin/main 6c1cb59)
- NEW `order-intake/core-kit-status.ts` — `CORE_KIT_STATUS_LADDER` + `coreKitTier()`:
  the one core `order_kit_status` → tier table; adds `kit_delivery_exception → kit_shipped`.

  `[ORDER_STATUS_KIT] unmapped core order_kit_status` when shipping is down and
  the core value is off-ladder.
- `grpc-client.service.ts` — `SampleDetails.orderKitStatus?` mapped from
  `sample.order.order_kit_status` in `listSample` ('' → undefined like PH-850 fields).
- No env / config / schema change. `kit` block still null when shipping degraded
  (approach A). Docs in repo: none describe the derivation (checked docs/, README).
