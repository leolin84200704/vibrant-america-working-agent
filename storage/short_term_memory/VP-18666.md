# VP-18666 - Work Loop Record

## Ticket Analysis

### [2026-10-02 18:40] Root cause FOUND: staging emr-v2 reads the DEV report service

- List status is derived from core order_info.order_report_status
  (deriveListStatus: report_ready/amended/delivered -> report_available).
  Staging core ListSamples 2454750: order 11308716, order_status
  order_completed, kit_lab_received, order_report_status report_ready,
  customer 3194, clinic 125613, created 2025-12-10T23:13:06Z.
- FHIR status comes from base-report getReportStatusListV2 via
  VIBRANT_API_BASE_URL (fhir-result.service.ts:347). Same barcode, same minted
  admin token, from inside the staging pod:
    base-report-dev-service     -> Analyzing Samples, generated 0/1, finished []
    base-report-staging-service -> Final Report Available, generated 1/1, VA
    base-report-service (prod)  -> 401 (dev secret, expected)
  => core is RIGHT, FHIR is reading the wrong environment's report DB.
- Why: AKS ConfigMap emr-v2/lis-emr-v2-config has
  VIBRANT_API_BASE_URL=.../base-report-dev-service, set by a `kubectl-patch`
  on 2026-09-10T22:49:35Z (12 keys in that patch; the managedFields entry for
  this key belongs to that patch). The gitignored local copy
  lis-emr-v2-config.yaml (June) says base-report-staging-service, same as
  LIS-transformer's non-prod default (trans.service.ts:25587). Prod CM is
  correct (base-report-service). No STM/journal records that 09-10 patch
  touching this key (grep base-report-dev: only VP-9299 table).
- Blast radius of the wrong URL on staging: every VIBRANT_API_BASE_URL
  consumer (fhir-result, report-pdf-client, result-generation
  getReportStatusListV2 + pdf, kafka report-finished listener, order-status
  report client, scheduled-reports csv) has been reading dev report data on
  staging since 09-10.
- Systematic: all 18 probed report_available rows of customer 3194 (Feb-May
  2026) are FHIR `registered` on sandbox; after the fix 2512106925 itself
  becomes the "accessible completed historical report" the PM asked for.
- Other local-vs-AKS CM drift (32 keys) is mostly node-IP repoints
  (10.224.0.199 -> 10.224.0.10) and keys added on one side; only
  VIBRANT_API_BASE_URL is a wrong-environment value.

### Injected lesson (ENGINEERING-LESSONS, sparse k=1)

- "null = unknown != empty != false" (spec-page lesson, line 70): an
  explicit degraded/absent state must never be collapsed into a neighbouring
  one. Here: patient-exists-with-zero-orders (empty) vs patient-not-visible
  (not found) vs upstream-failed (unknown) are three states the list path
  currently folds into one 404.
