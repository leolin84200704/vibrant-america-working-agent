# VP-18771 - Work Loop Record

## Ticket Analysis

### [2026-10-12 11:00 PT]
- **Ticket** (Yekai, 2026-10-09, Dev To Do, P2, parent VP-17348, tested by QH-7625): gRPC server must read `authorization` from gRPC metadata, pick HS256 (JWT_SECRET) or RS256 (oauth-jwt-rsa public key) by the token's `alg`, pin `algorithms` to that one alg, reject `none`; require a service identity (`internal_user_name`) instead of the HTTP customer/clinic checks; log-only first, then enforce; UNAUTHENTICATED on failure, never 500; HTTP auth unchanged. Ticket asked to confirm first whether the guard rejects every gRPC call or lets everything through.
- **改前 — CONFIRMED: effectively unauthenticated.**
  - `src/main.ts:45` `app.connectMicroservice({transport: GRPC, package 'resultgeneration', ...})` with NO second argument. `@nestjs/core/nest-application.js:127-133`: `inheritAppConfig` undefined -> `new ApplicationConfig()` for the microservice, so the `APP_GUARD` JwtAuthGuard (`src/app.module.ts:58`) is never attached to RPC handlers. Controller-level `@UseGuards` metadata IS honoured on RPC (`@nestjs/microservices` rpc-context-creator builds guards from controller/handler metadata — CON agent verified lines 33-64).
  - Prod evidence (Datadog `service:lis-emr-v2-deployment-prod`, 7d to 2026-10-12): 1152 `[generateResultHl7] sample=... ✓` lines, 381 `enter` lines; `JWT authentication failed` only 6 lines total (HTTP paths). Neither gRPC controller has @Public/@UseGuards (`result-grpc.controller.ts:75`, `reference-range.controller.ts:5`).
  - gRPC handlers: `ResultGrpcController` GenerateResultHl7 / GenerateBatchResultsHl7 / GetResultStatus / GetSampleByOrderId / GetHl7Content; `ReferenceRangeController` GetPatientDetailedReferenceRangeInOutBatch. Controllers catch handler errors into `{success:false}` responses.
  - Key material already in place: `JwtStrategy.selectVerificationKey(raw, JWT_SECRET, FHIR_JWT_RS256_PUBLIC_KEY)` (`src/modules/auth/strategies/jwt.strategy.ts:55-69`, VP-17450) picks by header alg; RS256 key present in BOTH live ConfigMaps.
  - Known external callers of the gRPC server: not found in any local repo for `resultgeneration` (LIS-transformer only references ReferenceRangeService protos). Caller inventory must come from the log-only phase (service-name metadata + token identity per call).
  - Reference implementations: results-grpc `src/auth/interceptors/metadataLogger.interceptor.ts` (enforcing, requires internal_user_name, `selectJwtKey`, `algorithms:['HS256','RS256']`); results-core `src/auth/jwt-auth.guard.ts` + `token-verifier.service.ts` (AUTH_MODE enforce/log, pins `algorithms` to the single candidate alg).
  - RpcException mapping (CON agent verified): guard must `throw new RpcException({ code: status.UNAUTHENTICATED, message })` — a plain `false` or a non-RpcException becomes UNKNOWN. Everything inside the guard (incl. header JSON.parse) must be caught.

## Approaches Considered

### [2026-10-12 11:40 PT] Debate (PRO/CON fork agents) synthesis
- **A (recommended)** — `GrpcAuthGuard` (`src/modules/auth/guards/grpc-auth.guard.ts`) bound with `@UseGuards` on `ResultGrpcController` and `ReferenceRangeController`. Reads `authorization` from `context.switchToRpc().getContext()` (= args[1], execution-context-host.js:32); strips Bearer; header alg must be HS256|RS256 (else reject, incl. `none`); key = `JwtStrategy.selectVerificationKey`; `jsonwebtoken.verify(token, key, {algorithms:[alg]})` (verify.js:144 rejects an alg outside the list); require `internal_user_name`. Mode env `GRPC_AUTH_MODE`: `enforce` -> `throw new RpcException({ code: status.UNAUTHENTICATED (16), message })`; anything else -> `log` (allow + one structured line `grpc_auth_check` {method, service_name, alg, outcome, reason, internal_user_name}). Whole guard body try/caught so nothing becomes UNKNOWN/500. Non-RPC contexts -> pass through (HTTP untouched; APP_GUARD still owns HTTP).
- Rejected: `inheritAppConfig: true` (drags every global pipe/filter/interceptor into the microservice and would run the HTTP-shaped JwtAuthGuard on RPC); interceptor instead of guard (guards are the Nest seam for auth and results-core uses a guard).
- PRO/CON both verified: @UseGuards metadata is honoured on RPC handlers without inheritAppConfig (rpc-context-creator.js:33-64); `false` from a guard becomes RpcException(FORBIDDEN) -> UNKNOWN(2), so the guard must throw with a numeric code; BaseRpcExceptionFilter passes object errors through (base-rpc-exception-filter.js:13-21), server-grpc.js:192 `callback(err)`, server-call.js:25-39 maps numeric `code`.
- Rollout: ship log-only; after >= 1 week build the per-caller histogram (service-name x identity x outcome) from the log line; flip `GRPC_AUTH_MODE=enforce` via ConfigMap (no deploy) once every caller sends a valid token. Known caller set today: none found in local repos for `resultgeneration` — the histogram IS the inventory.
