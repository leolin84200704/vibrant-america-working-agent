## Approaches Considered

### The decisive verification (2026-09-28, live prod gRPC)
An Explore agent's cost analysis concluded the report-release date was NOT available and would need
a new `getReportStatusListV2Batch` fan-out (~210-250 ms per cold barcode on the portal's hottest
endpoint — the exact shape VP-18197 had to back out). It correctly flagged that conclusion as
UNVERIFIED, because the fields are declared on the proto but unread anywhere in `src/`.

Verified directly against prod `InitialPatientPageHome` from inside the trans prod pod, using the
LBS-1799 order whose real dates were already known — **all three dates are present and correct**:

| field | payload | LBS-1799 prod ground truth |
|---|---|---|
| `order_service_time` | 2025-12-01 23:34 | service date 2025-12-01 |
| `samples[].sample_collection_time` | 2026-08-25 14:17 | collected 2026-08-25 |
| `samples[].sample_received_time` | 2026-08-26 21:34 | received 2026-08-26 |
| `samples[].sample_report_time` | 2026-09-03 04:07 | reported 2026-09-03 |

Also on the order: `order_report_status='report_delivered'`, `last_activity_at=2026-09-03 13:48`.

**Gotcha that cost two attempts: the array is `samples` (plural), not `sample`.** The proto message
is `samples` and the order key is `o.samples`; `cleanOrderlitenew` iterates it. Anyone probing this
RPC with `o.sample` gets an empty list and will wrongly conclude the data is absent — which is very
likely why the fields were assumed unavailable.

**Consequence: this ticket needs ZERO extra upstream calls.** It is pure computation over a payload
`cleanOrderlitenew` is already walking. The expensive option (a) is off the table.

### Shape problem the ticket does not address
`patient.Order[]` is **one row per SAMPLE, not per order** (documented in-code at
`getPatient.service.ts:367-368`; `cleanOrderlitenew` loops `samples`). But the ticket's rule is
order-level ("Multiple samples or recollection — use the most recent collection date"). So the three
maxima must be computed once per ORDER from `o.samples[]` BEFORE the per-sample loop, and the same
verdict stamped on every row of that order — not computed per row.

### Known landmine
`getPatient.service.ts:2800` does `new Date(order_create_time).toISOString()`; with both time fields
empty this throws and `cleanOrderlitenew`'s try/catch swallows the WHOLE order silently. Any new
date parsing must not copy that pattern.
