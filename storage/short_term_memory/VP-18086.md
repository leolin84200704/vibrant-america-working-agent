## Baseline (current behavior, from real code + prod data, 2026-09-03)

### Where the host rule lives
- `lis_pricing.exceptions` (type ADDITION_ENABLE, item_id = add-on, affected_item_id = host packagePriceId). "Add-on is selectable only while at least one affected host is selected; otherwise it is deselected and locked."
- Consumers of the SAME rows:
  1. Quote: pricing `service/quote.go ComputeQuote` -> `loadBestDealSupport` reads `Exception.Query().Where(IsNew(true))` -> `HandleException` (additionEnableException) -> `HandleBloodSalivaAddonException` -> engine. A removed add-on is dropped SILENTLY: no failure code, quote returns eligible with the remaining items priced. (createQuote returns eligible:false ONLY from the eligibility-check API, never from ComputeQuote.)
  2. Order: emr-v2 `parser.service.ts assembleWithNyRouting` -> order-team BestDeal API (`/v1/bestdeal/GetBestDealSuggestion`, va-portal `server/` extract of the same JS: handleException.mjs + getExceptionMap.mjs + geneticAddonConstants.mjs). Dropped add-on -> `accountBestDeal` dropped -> `no_orderable_items` 422 with errorCodes (PH-860 fail-closed).
  3. Portal UI: `NewVwTestTabPane.vue filteredGeneticsCategory` shows blood versions only when a blood host makes them eligible AND the order is not DBS; otherwise shows saliva versions ("DBS version always keeps saliva addons", commit d9db9c3a8 2026-02-04 by jiafanqian, from VP-14202 restricted add-ons).
- emr-v2 has NO add-on/saliva logic of its own (grep SALIVA/addOn in src = 0 hits outside auth/kafka).

### The data (prod lis_pricing, 2026-09-03)
- items 861 ApoE (Blood) / 863 MTHFR (Blood) / 865 FACTOR II-V (Blood): is_blood=1, tube EDTA; 862/864/866 saliva versions: is_blood=0, tube SALIVA. All 6 is_orderable=0 (add-on only). external_codes APOE_BLOOD..FACTOR_II_V_SALIVA -> 861..866.
- ADDITION_ENABLE: blood trio share one list of 36 blood-draw hosts (Wheat Zoomer, FSC, Tick Borne, Neural Zoomer Plus, Nutrient Zoomer, Foundation Zoomer, Celiac Genetics ...). Saliva trio share one list of 22 hosts: urine 9 (181 HEAVY_METALS_URINE, 196 ENVIRONMENTAL_TOXINS, 197 ORGANIC_ACIDS, 674 PFAS_CHEMICALS, 719 MYCOTOXINS, 823 OXIDATIVE_DAMAGE_MARKERS, 844 TOXIN_ZOOMER, 854 CELLULAR_ZOOMER), DBS/fingerprick 8 (586 WHEAT_ZOOMER_DBS, 588 TICK_BORNE_DBS, 590 TICK_BORNE_1_0_DBS, 612 FSP1 DBS [no code], 644 FOOD_SENSITIVITY_COMPLETE_DBS, 660 VIRUS_INFECTION_PANEL_DBS, 665 NEURAL_ZOOMER_DBS, 858 FOOD_BUNDLE_DBS, 860 FOOD_ZOOMER_DBS), 850 NUTRIENT_ZOOMER_MICROTUBE (BLOOD_MICROTUBE), 845 GUT_ZOOMER (stool+urine), 846 HORMONE_ZOOMER (saliva+urine), 724 TOXIN_GENETICS (SALIVA), 822 ANTIOXIDANT_GENETICS (SALIVA).
- => The existing rule is "blood add-on when the kit already draws venous blood; saliva add-on for every kit that does not" — a kit-logistics rule (the genetic swab ships with the kit), not a specimen-match rule. Exactly what the PM lists as failures is the deliberate allow-list.
- Catalog hosts whose tube requirement is actually saliva: TOXIN_GENETICS, ANTIOXIDANT_GENETICS, HORMONE_ZOOMER (saliva OR urine collection). Under the ticket's rule the saliva add-ons would drop from 22 hosts to these 2-3.
- Catalog (`GET /item/catalog/products`, model.CatalogProduct) does NOT expose sampleType; productMap returns {item_id,item_type} only. Sample type exists internally as `item_tube_requirements` x `tube_types` (enum SALIVA*, is_blood, requires_no_volume) and surfaces only in the menu `sampleTypeList`.

### Claim check: "blood add-ons already behave correctly"
- Order side: true by accident of the data — 861's list excludes DBS hosts, BestDeal drops it, emr-v2 fails closed (no_orderable_items).
- Quote side: FALSE — proven by read-only sandbox probes 2026-09-03 (api-sandbox /v1/quote, test client 3194, patient 3227402):
  - ["APOE_BLOOD","WHEAT_ZOOMER_DBS"] -> 200 eligible:true isDbs:true, lineItems = WHEAT_ZOOMER_DBS only, total 300 (add-on silently dropped, no error).
  - ["APOE_SALIVA","WHEAT_ZOOMER_DBS"] -> 200 eligible, both items, total 370 (matches Nan's test).
  - ["APOE_SALIVA","TOXIN_GENETICS"] -> 200 eligible, both, total 470 (a real saliva host — works today).
  - ["APOE_SALIVA"] alone -> 200 eligible:true, lineItems [], total 0 (silent drop to an EMPTY quote — a defect on its own).
  - ["APOE_BLOOD","WHEAT_ZOOMER"] -> 370 with free Total Immunoglobulins; ["APOE_SALIVA","WHEAT_ZOOMER"] -> 300, saliva silently dropped (blood host does not enable saliva version).
  - => quote has the PH-860 silent-drop problem emr-v2 already fixed on the order side; that is a pricing (Rui) defect independent of the saliva rule.

### Who owns the exceptions data
- pricing repo only READS exceptions (`BundleService.GetAllExceptions`); no Create/Update code in the repo. Rows are maintained outside pricing code (order-team / admin data). Changing the 862/864/866 lists is a data change that flips quote, order AND the portal menu at once.

## Approaches Considered
### [2026-09-03] Options put to Leo (Step 4 pause — premise conflicts with the current product rule)
- A. Data-only: shrink ADDITION_ENABLE lists of 862/864/866 to saliva-tube hosts (724 TOXIN_GENETICS, 822 ANTIOXIDANT_GENETICS, 846 HORMONE_ZOOMER). One change fixes quote + order + portal consistently; no emr-v2 code. But it reverses the deliberate portal design (saliva swab add-on on DBS/urine/stool kits) — PM + lab/kit ops must confirm.
- B. Code rule at both API edges only (pricing ComputeQuote + emr-v2 enrichment): saliva add-on requires a host whose item_tube_requirements include a SALIVA* tube. API diverges from portal; emr-v2 has no sample-type data -> needs pricing to expose sampleType on productMap/catalog first (Rui). Two repos, sequencing dependency.
- C. Independent of A/B: quote must fail closed on dropped items (eligible:false, no_orderable_items, errorCodes) like emr-v2 PH-860 — pricing/Rui.
- Recommendation: A if PM confirms the rule is specimen-match; C regardless; B only if PM explicitly wants API-only divergence.
