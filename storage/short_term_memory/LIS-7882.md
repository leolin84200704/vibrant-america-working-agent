## Ticket Analysis

### [2026-09-30 12:10]
- **Ticket** (LIS project, Task, P2, due 2026-10-05, sprint Team Yekai 30, reporter Yuchen Wang, assignee Leo): "When lis-backend-emr-v2 calls result grpc, please include Vibrant Oauth2 token". Links: blocks VP-18411 (Yuteng: turn on blocking in results-grpc for callers without OAuth2 name), tested by QH-7396. Attachment = Slack DM from Yuteng Fu 9:50 AM asking LIS-backend-v2-payout and lis-backend-emr-v2 to carry the token.
- **Source of truth** = Confluence "gRPC Caller Metadata Audit" (Yuteng, refreshed daily). Expected metadata `{Authorization: Bearer <JWT>, service-name, x-request-id}`. emr-v2 row: method `getTestsResultsRelatedDataWithDetailParse` (= server log name of proto rpc `getTestsResultsDetailData`), caller `lis-backend-emr-v2-production`, missing **Authorization + x-request-id** (service-name present), 33 calls in the 24h window.
- **Blocking rule that VP-18411 will turn on** (VP-18528, Dev To Do, Yuteng): reject only when NO service-name in metadata AND none in token payload; missing x-request-id stays a warning. emr-v2 always sends service-name, so emr-v2 would NOT be rejected even without a token; the ticket is still explicit about carrying the token.
- **Server today** (LIS-backend-results-grpc main efdf8a2, `src/auth/interceptors/metadataLogger.interceptor.ts`): no token -> pass with warn `gRPC missing token`; token present but undecodable/unverifiable -> `RpcException(Unauthorized)` **BLOCK**. Key selection `selectJwtKey`: HS256 -> shared JWT_SECRET, RS256 -> JWT_RS256_PUBLIC_KEY. So an **empty or expired Bearer is worse than none**.
- **Caller side in emr-v2** (worktree at origin/staging 9fec7d0): two call sites in `src/modules/grpc/services/grpc-client.service.ts` — `getTestResultsDetailedDataCloud` (testResultCloud, 10.224.0.10:30600 primary) and `getTestResultsDetailedDataSingleAttempt` (testResult on-prem 192.168.60.6:30600 fallback, retry chain). Both copy `grpcMetadata` from `src/config/grpc.config.ts:277` = only `service-name: lis-backend-emr-v2-${NODE_ENV}`. Caller = `sample-test-result.service.ts:147` (result generation path, Kafka-driven, no inbound HTTP context).
- **Token minting already exists in emr-v2**: `shortcut.service.ts` `getAccessToken()` — client_credentials POST to `OAUTH2_TOKEN_ENDPOINT` (default api.vibrant-wellness.com/v1/oauth2/token) with `OAUTH2_CLIENT_ID`/`OAUTH2_CLIENT_SECRET` via ConfigService, simple cache with 60s safety, 15s timeout, no dedup / negative cache. Those 3 env keys are present in BOTH local ConfigMap copies (prod + staging). Client id prefix `MjM2ODRk...` (emr-v2's own, differs from results-web/results-grpc which use the Cloud Report client `MGI5NWQ3...` via npm `vibrant-oauth2-client` + env VIBRANT_CLIENT_ID/SECRET).

## Approaches Considered

### [2026-09-30 12:40]
- **Probe addendum (on-prem fallback 192.168.60.6:30600)**: garbage Bearer is NOT blocked (sample 2600000 OK with `Bearer not.a.jwt`) -> on-prem lis-test-connect runs an older image without MetadataLoggerInterceptor; adding a token cannot break the fallback. Side finding: on-prem returns `Internal server error` for real samples 2555493 / 2641983 regardless of auth (cloud returns 467 / 99 tests) -> on-prem fallback is unhealthy today, independent of this ticket.
- **A (recommended, minimal)**: new `OAuth2TokenService` (ConfigService `OAUTH2_*`, cache with 5-min safety, in-flight dedup, 10s fetch timeout, 60s negative cache, throws when no token) injected `@Optional()` into `GrpcClientService`; one `buildResultsGrpcMetadata()` used by both results call sites (metadata is already built per attempt): service-name + x-request-id (randomUUID) + authorization when a token is available. Fail-open = omit authorization, WARN + damped Sentry message with running counter (emr-v2 has Sentry, no Datadog metrics). On RPC error `Invalid authorization token` -> clear token cache so the next attempt mints fresh. ShortcutService untouched (follow-up dedupe).
- **B**: A + ShortcutService delegates to the shared service (PRO: one cache per process, removes duplicate minting; CON: order-intake blast radius, scope creep, reviewer rejected over-built PRs before) -> not recommended for this PR.
- **C**: sibling convention npm `vibrant-oauth2-client` (VIBRANT_CLIENT_ID/SECRET, process.env only) + strict-by-default with GRPC_OAUTH_FAIL_OPEN -> needs new ConfigMap keys in both clusters and a second OAuth client identity in the same pod; strict default turns an OAuth outage into results not delivered while the server does not even require the token -> rejected.
- **Debate synthesis**: PRO insisted on `@Optional()` injection (4 specs `new GrpcClientService()` zero-arg) and on probing on-prem (done). CON insisted on mint-per-attempt (already the case), cache drop on auth reject (adopted), fail-open must be observable (adopted via Sentry), do not touch ShortcutService (adopted), x-request-id explicit (kept, flagged to Leo).
- **Lesson followed**: fail-open gate gets a counter (ENGINEERING-LESSONS 29); verified live, not mock (probe both endpoints, grader validated with garbage token).
