# VP-18593 - Work Loop Record

## Ticket Analysis

### [2026-09-30 17:20] Origin
Leo, after VP-18589: 「我們tracking status 是直接接fedex? carrier、shippedAt、deliveredAt
感覺應該要有？」 then 「要，這是嚴重的問題。請改善，doc + comment也要改」.

Four-part:
1. 目的 — the documented kit block (carrier / trackingNumber / shippedAt / deliveredAt)
   was cut to status + trackingNumber on 08-13 (VP-17760 c.183880/183942) as "no
   upstream has them". Wrong for two of three.
2. 改前 — LIS-Shipping origin/master: FedEx EDI status feed → Azure Service Bus
   (`handleFedexTrackingUpdates`) → `fedex_tracking_updates` + `client_transaction_shipping`
   (kit_status, current_status = FedEx text, fedex_delivery_date); raw FedEx events in
   prisma8 `fedex_shipping_status` (last_status_code PU/DL…, delivery_date/time,
   delivery_attempt_exception); DHL in `dhl_tracking_events`. `queryKitStatus` builds
   `Packages.url` by its own rule (12-digit → fedex.com, 10-digit → dhl.com) and
   `pickup_time` = `retrieveTrackingPickupTime` (earliest PU scan, LA-local → UTC ISO)
   || po_create_time. Proto field 5 `pickup_time` exists in LIS-Shipping /
   LIS-transformer / cloud-local-proxy protos; emr-v2's two copies had 4 fields →
   proto-loader dropped it. Delivery time is in the DB but NOT in the RPC.
3. 改後為何有效 — read url + pickup_time; carrier from the URL host (single source of
   truth = shipping's rule); shippedAt only once rank ≥ 1 (READY's pickup_time is just
   the PO create time). deliveredAt stays null until shipping extends the RPC.
4. 改什麼 — see Code Changes.

Docs: mintlify already documents all five fields (that page was never updated for the
08-13 cut); Confluence 2485977089 v24 (today, VP-18589) says the three were dropped —
must be corrected again to "carrier + shippedAt live, deliveredAt pending shipping".

### [2026-09-30 17:20 PT] INCIDENT (self-inflicted): exponent-formatted sample_id sent to shipping
- A shipping-side colleague traced 22 GetKitStatusBySampleId calls (23:24:58-23:25:43Z) whose
  sample_id arrived as "2.5983e+06": V2 ListSamples rejects (strconv.Atoi, code 2), shipping
  falls back to V1 which Number()s it -> 2598300, i.e. possibly a DIFFERENT sample. Read-only,
  nothing written.
- Source = THIS session's two exploratory range sweeps from the prod emr-v2 pod (scratchpad
  probe.js, 23:24:35Z `seq -s, 2598230 2598275` and 23:25:25Z `seq -s, 2598276 2598420`).
  macOS /usr/bin/seq (BSD) prints with %g, so every id >= 1e6 came out as 6-significant-digit
  exponent text; each block of 10 ids collapsed into one string, so the sweep effectively
  queried only the multiples of 10, each 10 times (191 requests, 20 distinct strings).
  probe.js forwarded argv verbatim into the proto string field.
- Blast radius on conclusions: NONE. The recorded evidence (2597500 / 2596000 / 2598251 /
  2598000, VP-18595's 2598251 DELIVERY_EXCEPTION + READY_FOR_RETURN, GetTrackingDetails by
  tracking number) all came from the 23:23Z runs with literal integer ids. The two sweeps only
  fed a status-combo tally that was never written anywhere (STM / Jira / Confluence grep clean).
- Prevention: generate numeric id lists with `seq -f '%.0f'` (or a shell loop / jot) on macOS,
  and make every probe harness reject ids that fail /^\d+$/ before sending. A gRPC string
  field accepts anything; the far side may silently coerce.
- Hardened reusable version committed: `scripts/probes/shipping-kit-status-probe.js`
  (validates /^\d+$/ before loading gRPC, dedups, default host:port, prints the seq -f hint).
  Verified locally: exponent ids -> refused exit 2; valid ids -> reach the send path.
