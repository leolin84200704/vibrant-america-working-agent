# VP-19019 - Work Loop Record

## Ticket Analysis

### [2026-10-23 15:10 PDT] Why it exists
- Leo asked whether VP-17827 + VP-18755 already make everything practice-level. They don't: the automatic push goes
  through `kafka-report-finished-listener.service.ts` `findEligibleResultIntegrations`. It reads LIVE result rows by
  `customer_id` only, sorted by `integration_type desc, updated_at desc`, and keeps the first row per
  (legacy_emr_service, sftp_result_path). The processor then uses that `integration_id` as is. VP-18755 fixed only
  `result-generation.service.ts` (preview / manual generate / API).
- Prod evidence (read-only): Next Health 43262 has 4 LIVE FULL_INTEGRATION rows (2930 / 8003 / 36290 / 144510, same
  folder `/Prod/FollowThatPatient/Results/`, 3 rows share the same updated_at). The last 12 auto pushes all used the 2930
  row (MSH-6 2930). Sample 2653369 was ordered at 144510 (report_finished event clinic_id 144510 = lis-order
  order_status_updates clinicId 144510) but went out with MSH-6 2930.
- HL7 order intake is still practice-aware only for FOLLOWTHATPATIENT (`practice-id-field.ts`). That is the 10-08
  policy, not a gap.

## Decisions Made

### [2026-10-23 15:20 PDT] Practice source
- report_finished / redraw_report_finished: use the event `clinic_id`. It is the order clinic, so no extra gRPC call.
- Partial pushes (sample_type_all_finish / new_report_status_updated): `resolveSampleClient` also reads core
  `order.clinic_id` through `listSamplesBatch`, the same source VP-18755 uses. Failure means no preference, so the old order applies.
- Rows at the sample's practice go first (stable sort), then the remaining rows in the old order. Dedupe is unchanged.
  The '-1' clinic-level fallback is unchanged.

## Related: VP-19017 (FE, Siyun) API gap analysis — 2026-10-23
- The 2 commits in `ehr-frontend` (ff88ee2 on staging, b54d265 on setting_ehr, no PR) only add a Practice Settings
  "EHR Integration" tab behind the `auto_emr_integration` beta flag. The tab reuses `ThirdParty/EMR/index.vue` with a
  `canEdit` prop and removes EHR from the Third-Party page. The banner, the Add Provider flow, the members table
  (Approve / Reject / Suspend) and the empty state are NOT built.
- What shipped needs no backend change. The endpoints already exist: GET vendor-management/ehr-vendors, GET/POST/DELETE
  auto-integrate/requests, POST auto-integrate/vendor-inquiries.
- Pre-existing FE bug: "Disconnect" (LIVE) and "Cancel Request" (IN_PROGRESS / APPROVED) call DELETE, but the service
  allows DELETE only for PENDING / REJECTED. The resulting 400 is swallowed, so the user sees nothing. The backend
  already has PATCH `:id/disconnect` and `:id/cancel`, so this is an FE wiring fix.
- For the full design the backend would need a list-members-by-clinic endpoint, practice-admin role checks, and
  approve / reject / suspend actions for practice admins. We would also have to decide whether those write
  `ehr_integrations` or the mirror tables. The admin read-only rule is FE-only today.
