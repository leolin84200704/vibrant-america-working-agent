# VP-18464 - Work Loop Record
## Findings (subagent, read-only, 2026-09-29)
1. Datadog has no nginx ingress access logs: `datadog/datadog-agent` DaemonSet `DD_CONTAINER_EXCLUDE` covers `app-routing-system` and `ingress-basic`. No `nginx_ingress_controller_requests` series for `cloud-local-ingress` either (other ingresses do have counts).
2. Only 36 h of controller access log via kubectl (controller restarted 09-28 06:12Z, no `--previous`). In it: 0 requests to `/v1/lis/cloud-proxy*` prod and -st (3 probe requests from us with UA `vp18464-readonly-probe/1.0` excluded).
3. Proxy pods log nothing per request except `old-report/checkIfPersonalizedReportCanBeCreated` (sample_id + result) and `oneClickPersonalizedReport` (sample_id). Datadog 15 d: ~101 calls 09-14 18:15–18:29Z (70 sample ids, 3 pods, ~7/min, Sunday 11:15 PDT — looks batch), then 0 through 09-29. Retention edge is 09-14 18:14Z so the burst was already running at the edge.
4. Not lis-trans: trans inlined cloud-proxy on 05-21 (`9fbe233`), its config points `checkIfPersonalizedReportCanBeCreated` at `192.168.60.77:8081` directly, and trans logs have 0 cloud-proxy URLs in 15 d. Caller identity unrecoverable: ingress logs only `$remote_addr` = Cloudflare edge IPs; `real-ip-header`/`use-forwarded-headers` are ConfigMap keys mis-written as annotations (no effect).
5. Second instance outside AKS: `https://www.vibrant-america.com/lisapi/v1/lis/cloud-proxy/` answers (200 root, 401 guarded) and never touches the AKS ingress. `LIS-backend-billing ProZOrderServiceImpl.java:115` hardcodes exactly that URL → billing calls the on-prem instance, not the AKS deployment.
6. Cluster config scan: only `default/lis-trans-config` had cloud-proxy URLs (the 14 stale keys — deleted today under VP-18461). No Deployment/CronJob/StatefulSet env references cloud-proxy.

## Blocked on
- On-prem ingress/access logs (Ray).
- A real ≥30-day zero window on cloud: un-exclude `app-routing-system` in the agent (or Cloudflare per-path analytics). Recommendation only, not done.
