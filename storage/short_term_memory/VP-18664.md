### [2026-10-02 18:40] Root cause (reproduced live, sandbox + staging core gRPC)

- Sandbox GET /v1/orders?patientId=3227432 -> 404 requestId 0ffd6f6c...; staging
  pod log: "Retrieved 0 samples for patient 3227432". Staging core (cloud
  10.224.0.10:30282, v1 lis) GetPatient 3227432 = {customer_id 3194,
  patient_customer_ids [3194], 0 samples}; GetPatientSamplesByTimeRange ->
  {sample_ids [], total_count 0}; unknown id -> gRPC NOT_FOUND "Active patient
  N not found" (GetPatient) / "Patient with ID N not found" (time-range).
- Code: order-list.service.ts listForPatient returns null when `inScope` is
  empty (`if (!inScope.length) return null; // 404 uniform`), i.e. it never
  asks whether the patient EXISTS and is LINKED to the token customer. Zero
  samples and foreign patient are indistinguishable by design (VP-18030).
- Existing seam: grpc-client.service.ts getPatientById (VP-18342, v1 client,
  cloud-primary/on-prem fallback, null on NOT_FOUND, throws otherwise), but
  mapPatientDetailsV1 drops customer_id / patient_customer_ids.
- Scope relation that /patients list uses (coreSamples listPatientRecords,
  patient.service.ts:3774+): customer scope = patient_customer some
  customer_id; clinic scope = patient_clinics some clinic OR patient_customer
  in clinic's customers. Both test patients appear in the clinic-scoped
  /patients list (count 2933).

### Injected lesson (ENGINEERING-LESSONS, sparse k=1)

- "null = unknown != empty != false" (spec-page lesson, line 70): an
  explicit degraded/absent state must never be collapsed into a neighbouring
  one. Here: patient-exists-with-zero-orders (empty) vs patient-not-visible
  (not found) vs upstream-failed (unknown) are three states the list path
  currently folds into one 404.

## Approaches Considered

### [2026-10-02 18:55] Debate outcome (2 subagents) -> design v2 = A with adjustments

- Pro: conflation is explicit in code (service :172 + controller :128-132);
  linkage relation matches ListPatientRecords customer scope
  (patient_customer some customer_id); seams = 2 grpc wrappers; 503 policy
  already in file.
- Critic accepted points: (1) pass timeoutSeconds 15 to getPatientById (list
  path convention; default 30 is wrong here); (2) GetPatient carries the full
  patient graph -> heaviest exactly on the shared-patient empty path; still
  bounded by one human's history and ListSamples already paid more; keep,
  measure on staging with patient 477769-class size; (3) tryCloudThenOnPrem
  verified: NOT_FOUND -> null never triggers fallback (isTransientGrpcError
  :1581-1586 only DEADLINE/UNAVAILABLE/UNKNOWN/INTERNAL) -> no false 404 from
  fallback; (4) uniform-404 rationale (no cross-tenant probing) preserved:
  linked -> 200 empty, not linked -> same 404 as unknown.
- Critic alternative kept as fallback: skip GetPatient when ids.sampleIds is
  non-empty (patient has orders only elsewhere -> uniform 404 as today). NOT
  adopted by default because such a patient still appears in the caller's
  /patients list (patient_customer link) and the contract says accessible
  patient with no orders = 200 []; adopt only if staging latency is bad.
- Mandatory staging E2E: linked+0 orders (3227432) -> 200 []; foreign patient
  (3227413 under 3194? re-pick) -> 404; unknown -> 404; shared big patient
  latency; legacy patient without patient_customer rows if one exists.
