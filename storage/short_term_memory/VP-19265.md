# VP-19265 - PNS token minted with internal_user_role 'admin'

## Source
- Zhiheng Wu DM to Leo 2026-11-09 15:29 PST (code scan finding on trans v1); Leo: "請處理". Ticket created by the agent (Bug, P1, Sev-1, due 2026-11-13).

## Findings (2026-11-09 23:50Z)
- Minting: trans `GET /patients/pns-jwt` -> `generatePnsJwt` (sample-patients.service.ts ~1510-1545): `{patient_id, customer_id, clinic_id, role:'patient', internal_user_role:'admin', iat, exp 6h}` signed with the shared HS256 login secret (`listSec()`). Ported from LIS-Sample by VP-18798 (commit 0126145a).
- Origin of the admin claim: LIS-Sample commit 2c50194 (LIS-5346, 2025-02-25, Zhihong Chen, "Billing - PNS Payment API: Added internal user role and customer ID"). The original LIS-4334 payload (2024-05-30) had no internal role.
- Why it is dangerous: isAdminRole/canReadPatient (patient-detail.authz.ts) and isTrustedInternalCaller (internal-caller.util.ts) admit 'admin'; CustomJwtAuthGuard accepts any token signed with the login secret on any route (VP-19088). The token is emailed to patients (LIS-Shipping NY waiver, orders.service.ts:18174) and put in the PNS payment URL (LIS-frontend SplitBill.vue), so the holder can read any patient's detail cross-tenant for 6 h.
- Callers of /patients/pns-jwt (trans prod 14 d): browser staff login tokens ~440 (LIS-frontend SamplePageStore.fetchPnsToken, PNS-Singlepage FedexPickupStore.getPNSTokenViaLISToken), LIS-Shipping axios/1.15.2 x3, agent curl.
- Where the minted token is presented (token-shape audit, exact claim set, 14 d): trans /trans/getPatientWaiverForm 3, /trans/waiverFormRequest 2 (both check sample.customer_id == token.customer_id), /utility/getSetting 25 via axios/1.16.0 (trans-v2 PNSResolver) and axios/1.19.0 (trusted flag only drives report_style_can_edit). Other targets from PNS-Singlepage: trans-v2 GraphQL UnifiedAuthGuard (no internal_user_role logic outside calendar), billing /nonBloodSampleTubeType + /customer/getCustomerInfo (no role check; billing isAdminToken only on /orderTest/patient GET/PUT and isTokenAllowedToAccessSamples, both with a customer/clinic fallback), payout getEligibilityOfBNPL, pricing getCountryList, LIS-Shipping pickups (JwtAuthGuard), lis-core /patient/merge-patients (PNS_HTTPInternalAuthGuard checks `role` in [admin, support, it, patient, accessioning]), trans /utility/sendLocationText|confirmAddress|updateCollectionStatus (no trusted gate). LIS-frontend cancelConciergeFee -> billing /orderTest/cancelSelectedConciergeFee (no role check). Billing EditOrderServiceImpl gates non-"add" edits on support/it/admin, but no PNS flow calls editOrder.
- Conclusion: no consumer needs the admin claim. Narrowest fix = drop `internal_user_role: 'admin'`; keep clinic_id. Purpose binding stays with VP-19088 Fix B.
