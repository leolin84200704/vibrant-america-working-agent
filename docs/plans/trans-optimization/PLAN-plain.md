> 這份是給沒有背景知識的人看的版本。技術細節、證據、檔案位置都在同目錄的 `PLAN.md`（v0.3）。

## 一、先用一句話說

**Trans 是我們系統的「總機櫃檯」。現在這個櫃檯接電話太慢，而且很多電話被轉接了三、四手才到真正能處理的人。我們要把多餘的轉接拿掉、讓櫃檯同時處理多件事，但櫃檯對外講的每一句話都要跟現在一模一樣。**

---

## 二、Trans 是什麼？為什麼不能直接把它拆掉？

把整個系統想成一家醫院：

- **Core** 是病歷室（金庫）。裡面放的是病人資料（PHI，受法律保護的健康資訊）。為了安全，病歷室決定「只跟內部人員講話」（只開 gRPC，不開一般網頁 API），外面的任何系統都不能直接走進去。
- **Trans** 是櫃檯。病人（前端網頁）要看報告、查訂單，都是問櫃檯，櫃檯再去病歷室、藥局、物流等各部門把東西湊齊，一次交給病人。

所以 Trans 有兩個不能拿掉的工作：
1. **守門**：它是病人資料唯一的對外窗口。
2. **湊齊**：前端問一次，它去跑好幾個部門，湊成一包回答。

我們有兩個櫃檯：`Trans v1`（舊，REST API）和 `Trans v2`（新，GraphQL）。兩個都在雲上（Azure），各 3 台機器在跑。

## 三、現在的問題是什麼？

### 問題 1：太慢
用 Datadog（監控系統）看，「一百個人排隊，第 95 個要等多久」（P95）這個數字很高。以 2 秒為標準，有 10 到 20 支 API 超過，尖峰時段更慢。沒有人有時間查原因。

### 問題 2：電話轉接太多手（會議上叫「套娃」）
2023 年剛搬到雲上時，雲上和公司機房（地上）之間的網路不通，像兩座島之間沒有橋。當時一位同事（雨萱）造了一艘**臨時渡船**叫 `cloud-local-proxy`，兩邊各放一艘，專門幫忙把請求划到對岸。

後來橋蓋好了（網路通了），但渡船一直沒收掉，還在載客。我們在正式環境裡實際找到的例子：

| 例子 | 現在的路 | 應該的路 |
|---|---|---|
| Trans v2 要問「這份報告能不能做個人化版本」 | Trans v2 → 渡船 → 機房的報告主機 | Trans v2 → 直接打機房的報告主機（Trans v1 早就這樣做了） |
| Trans v2 要查試劑盒狀態、檢驗狀態、問卷 | Trans v2 → Trans v1 的網頁 API → Trans v1 再打病歷室 | Trans v2 自己就有病歷室的專線，直接打 |
| Trans v1 要問同一個雲上叢集裡的 40 多個服務 | 先跑出大門走公共馬路（公網、TLS、防火牆）再繞回同一棟樓 | 走室內走廊（叢集內部網址）。Trans v2 對同一批服務已經是走室內 |
| 帳務系統（billing，Java）要送皮膚檢測訂單 | 帳務 → 機房那艘渡船 → 病歷室 | 帳務 → Trans v1 的同一支 API |

另外還發現一大堆「早就沒人打了但還留在電話簿裡」的舊號碼：Trans v1 有 14 個、Trans v2 有 8 個設定值指向渡船或指向根本連不到的舊 IP，程式裡已經沒有任何地方會讀它們。

### 問題 3：電話簿常被人不小心蓋掉
Trans 的設定（ConfigMap）有 150 多筆，多數是「某個服務的地址」。全公司工程師都有寫入權。已經發生過好幾次：有人拿自己電腦上的舊檔案整份覆蓋上去，把已經改成雲上的地址又改回機房。

### 問題 4：沒有自動品管
兩個 Trans 的部署流程是「程式推上 main 分支就自動上線」，中間**沒有任何自動測試**。我在本機跑現有測試，Trans v1 有 17/46 組失敗、Trans v2 有 7/52 組失敗（多數是環境和過期的假資料，不是真 bug，但表示這條防線現在是壞的）。這代表：現在任何人說「我這次改動不影響功能」，都只能靠人眼比對。

### 問題 5：兩個「孤兒」服務
Ray 今天補了兩個也要處理的 repo：
- **`cloud-local-proxy`**（渡船本尊）：18 條路由，**每一條在 Trans v1 裡都已經有一份同樣的實作**。也就是渡船上的每個功能，櫃檯早就會了。
- **`web-homepage-api`**（機房裡叫 `vw-page`）：72 條路由，其實是**公司官網（vibrant-wellness.com）的後台**——訂閱電子報、聯絡我們、徵才、網路研討會、教育中心。跟 LIS 有關的只有 3 條（記錄報告被「看／下載／分享」了幾次）。
- 兩個都是同一位已離職同事手動部署的，沒有正式的自動部署，部署腳本裡用他的個人帳號登入機房、還寫著明文密碼。

## 四、我們要做什麼、不做什麼

**要做的四類事**
1. 把多餘的轉接拿掉（換電話簿裡的地址，或讓 Trans v2 用自己的專線）。
2. 讓櫃檯「同時」去問各部門，不要問完一個再問下一個。
3. 配合 Core 團隊退休舊病歷室：把 Trans 還在用舊病歷室「一般網頁 API」的 4 個地方改成走專線（VP-17348 / VP-18152，10 月 31 日前）。
4. 把該退休的渡船退休。

**絕對不做的事**
- 不改任何 API 對外的回答格式、錯誤碼、欄位。
- 不改資料庫結構。
- 不繞過任何權限檢查（誰能看哪個病人的資料）。
- 不重寫、不合併 Trans v1 和 v2。
- 每一步都要能一鍵退回。

## 五、怎麼保證「功能不變」？（這是整個計劃最重要的部分）

用四道防線，缺一不可：

1. **先量再改**：沒有 Datadog 的排名之前，不挑端點。每張票要寫「改之前多慢、目標多快、怎麼量」。
2. **自動品管門**：部署前一定跑測試和型別檢查，紅燈就不准上線。第一件事是先把現在壞掉的測試修好。
3. **對答案（shadow diff）**：對每個要改的端點，把同一批請求同時丟給「舊版」和「新版」，把回答逐字比對，**差異必須是零**才准切換。這是 Core 團隊遷移時用過的方法。
4. **契約快照**：把 API 的「說明書」（Swagger、GraphQL schema）存起來，每次部署自動比對，刪欄位或改型別就擋下。

另外兩條紀律：
- 電話簿只用 `kubectl edit` / `patch` 改，禁止整份 `apply`；改之前先把現況存一份。
- 一張票一個 PR，PR 開出去就不再往上推 commit。

## 六、分六個階段做

### 階段 0：量測與防護網（先做，不碰任何正式環境的行為）
- 做 Datadog 儀表板，列出**最慢的 20 支 API**（以 P95 × 使用量排序）。
- 修好兩個 repo 現有的測試紅燈。
- 部署流程加上「測試沒過不准上線」。
- API 說明書快照進 CI。
- 把 4 份電話簿（正式／測試 × v1／v2）存檔當基準，寫一支每天比對的腳本。
- 做一套「錄請求、重放、對答案」的工具。

> 完成標準：兩個 repo 測試全綠、CI 會擋紅燈、有 Top-20 清單、有基準電話簿。
> 風險：幾乎為零。

### 階段 1：換電話簿（大部分不改程式）
- Trans v2 的「個人化報告能否產生」改成直接打報告主機（跟 v1 一樣）。
- 清掉 22 個沒人讀的舊號碼。
- Trans v1 走公共馬路的 55 個地址，**一個服務一批**改成室內走廊，每批先在測試環境驗。
- Trans v2 查試劑盒／檢驗狀態／問卷改用自己的專線（要改程式，但邏輯逐行照搬 v1，並對答案）。
- 渡船退役：拉兩邊的 ingress 存取紀錄找出所有還在用的人 → 逐一改指向（含帳務系統那一支）→ 流量歸零 30 天 → 兩個叢集都關掉 → 封存 repo。

### 階段 2：讓櫃檯同時辦事（改程式，但語意不變）
只用四種手法：串行改並行、一筆一筆查改成一次批查、同一個請求內不重複問同一件事、對已有快取的地方調長一點時間。以階段 0 的 Top-20 為準，一支 API 一張票，每張都要對答案零差異。

已知候選：找病人列表（findPatient）、時間軸（getTimeLine）、病人檔案頁（patientProfile，同一個樣本問了 4 次）、病人通知頁（PNS，一次要問 19 個欄位）。

### 階段 3：配合病歷室 v1 退休（Core 團隊的票 VP-18152）
讀完 Jira 之後這一段改寫了。Core 團隊的做法是**在病歷室那一端**做切換：舊病歷室（v1）收到請求後自己轉給新病歷室（v2），櫃檯完全不用改。所以我們原本想「在櫃檯做一個 v1/v2 開關並雙打對答案」的做法**撤回**，做了會跟他們重工。

Trans 真正要做的只有一件事：Trans 還有 4 個地方在用舊病歷室的「一般網頁 API」（不是專線），這種 API 10 月 31 日會被刪掉。要在那之前改成走專線。其中 2 個是「新建病人」的寫入，2 個是「查診所底下的客戶」。查詢那支要等 Core 團隊先驗完新病歷室的對應功能（VP-18144）。

另一個約束：這段期間**不能改動 Trans 裡那份病歷室的通訊協定檔（proto）**，因為新舊病歷室之間的轉接靠的就是兩邊協定完全一樣。

### 階段 4：機器與體質（可與階段 1 並行）
補 CPU/記憶體上下限、自動擴縮（HPA）；Trans v1 每個請求都把整包內容寫進 log 的行為改成只記大小（**Leo 已拍板：這不算功能變更**）；渡船若暫時不能退，至少釘版本、加健康檢查。

### 階段 5：純轉接端點的退場（需要前端與 PM 一起決定）
Trans v1 有 36 條端點只是把網頁請求轉給報告服務。分三類：有權限檢查的保留；純轉接的讓前端直接打目標，Trans 先加「還有人在用」的紀錄，歸零 30 天再拆；Trans 自己的 gRPC 服務有 3 個內部使用者，不拆。

**Track W（`web-homepage-api` 的去向）** 也放在這個階段，見下面第 D6 題。
