# VP-18824 — Cerbo says HL7 only; the VP-18194 canary was the cause

## What Leo asked
Bare ticket id. Then: "做了以後會讓 hl7 file 包含三個pdf file 的編碼嗎？" (no — A/B only stop loose
files; three PDFs in one HL7 is the encoder change, option C). Then: "A 先做，B 也做，C 寫進
comment 請 integration 側問 Cerbo". Then: "push pr, 直接comment".

## Path of the investigation
1. Jira + Zendesk #769911 read first. Cerbo's Anne (ticket 572378) stated the rule verbatim:
   hl7 files only, no isolated PDFs, PDFs embedded in the message.
2. Provider 28524 / clinic 127660 rang a bell — grep of STM found VP-18194's canary was exactly
   that practice (the SIIR-291 origin). prod `ehr_integrations`: it was the ONLY row in 1136 with
   `split_result_pdf_by_report` set. So the ticket was not a new Cerbo behaviour, it was our own
   3-week-old canary finally getting its answer.
3. `result_attachment_records` REPORT_PDF rows: first 2026-09-25, 14 orders, all DELIVERED. HL7
   sizes 4.7-5.5 MB => the combined PDF was still embedded; the HL7 was never the problem.
4. Peer-verified on Cerbo's SFTP with the vendor account (paramiko listdir only). Decisive find:
   Cerbo renames a consumed HL7 to `{accession}_{YYYYMMDDHHMMSS}.hl7` in `archive/` — the suffix
   is THEIR import time (US/Eastern). Before 09-25 every file was consumed within hours; after
   it, 12 of 14 carried the same 2026-10-13 16:14 suffix = cleared by hand today. Pattern matches
   "poller walks the listing in name order and aborts at the first non-.hl7". That one listing
   answered three questions at once: no cleanup needed (folder empty), no repush needed (all
   consumed today), and the urgency (next push would re-stall).
5. Code: `resolveDelivery` -> pure `resolveReportPdfDelivery` is the single decision point for
   both the loose per-report files and the combined-PDF embed gate; the VP-18138 order-summary
   file has its own vendor-flag gate. A vendor-level HL7-only flag slots in above both.

## Decisions and why
- A (config rollback) first because her cadence is several pushes a week and the next one would
  stall Cerbo again. Done in a guarded transaction with the in-txn whole-table invariant.
- B (guard column) because PM had asked twice to enable this practice and the MDHQ vendor row
  covers 202 clinics; without a code-level invariant the rule lives only in memory.
- C (multi-PDF-in-HL7) deliberately not built: shared encoder, and Cerbo's parser behaviour for
  multiple ED OBX is unknown. Asked on the ticket with three concrete questions.
- No repush: Cerbo ingested the 12 today; Leo's cross-ticket "以前的不管了" rule.
- Merged #477 to staging myself (2026-10-03 rule); staging -> main release PR is Leo's.

## Things that went wrong
- Migration UPDATE keyed on `id = 1 AND code = 'MDHQ'` (copied from prod). Staging has MDHQ at
  id 106 -> 0 rows. The apply script's 100% verify exited 3 and caught it; re-keyed on `code`.
- First kubectl exec used container name `lis-emr-v2` (actual: `lis-emr-v2-prod` /
  `lis-emr-v2-staging`); first staging poll used label `app=lis-emr-v2-deployment-staging`
  (actual: `app=lis-emr-v2-staging`). Both cheap, both avoidable by reading the pod spec first.
- The wrong-label poll loop and the corrected one append to the same log file; harmless.
